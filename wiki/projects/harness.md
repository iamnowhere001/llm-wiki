# Harness Engineering

> 把「Agent 老犯错」从「再试一次」变成「工程上让它不可能再犯」。

- **目标（可验收）**：把 Harness Engineering 编译进本库 —— 讲清它的**演化历程 / 定义边界 / 业界实践**，以及**个人如何深度理解它、如何高效实践**，达到「个人读者读完能自己搭出一套最小 harness」的深度
- **验收判据**：四个维度各有一组能被独立追问的答案（**谁说的 / 凭什么 / 边界在哪**），而不是四段综述；且缺口表清空
- **交付物（2026-09-19 裁定后明确）**：**库内研究页** [[harness-explained]]（`analyses/`），读者是北洛本人与本库。**验收方式**：四维度各有正文、每条断言可追到素材或显式标为「本库推断」、边界与反方单列成节
- **终点**：「当前缺口」表清空即 `shipped`。之后若新素材开的是新缺口，**另开一个项目**，本项目不复活
- **阶段**：`active`（2026-09-19 起）—— 交付物形态与验收方式已由北洛裁定明确，见「决策记录」最后三条。**此前停在 `planning` 的唯一原因即「产出形态未定」，该原因已消除**
- **起始**：2026-09-19
- **目标完成**：—

> 从「值不值得」的**判断题**，改成「怎么理解、怎么做」的**实践题**。本页相应位置已同步。
>
> **与 [[llm-wiki-research]] 的界线**：那个项目问「**知识怎么编译**」（PKM 视角），本项目问「**agent 怎么不犯错**」（AI 工程视角）。
> **两者在 [[agents-md]] 上交叠** —— 它既是本库的规则文件，也是 harness 的第一种形式。
> **划界方式**：本项目**不重复论证「为什么要让 LLM 维护知识库」**，只回答「已经用了 agent 之后，怎么让它可靠」。
> 交叠处的处置写进「不做什么」。

## 知识（本项目消耗的页面）

> 项目与知识库之间的正向连接。这里链到的页面，就是「服务于本项目」的页面。

- **核心概念（2026-09-19 随四篇一手新建）**：[[harness-engineering]]、[[guides-and-sensors]]
  > [[harness-engineering]] 是本项目的概念主干 —— 四篇一手素材全部汇入它。
  > [[guides-and-sensors]] 是 Böckeler 的控制机制二分。**它给了本库两个此前不相关的机制一个共同的上位概念**：
  > `AGENTS.md` 是 guides（前馈），[[wiki-lint]] 是 sensors（反馈）。本库此前从没把它们放在一起看过。
- **人物线**：[[mitchell-hashimoto]]（命名者）、[[birgitta-bockeler]]（最系统的分析者）
  > 两人各有一个「诚实之处」值得记：Hashimoto 自陈**不确定这是不是业界通用术语**；
  > Böckeler 自陈**这个隐喻撑不住**（"Metaphors only go so far"）。
- **枢纽 —— 两个项目的交点**：[[agents-md]]
  > Hashimoto 把 harness 的第一种形式定义为「改 `AGENTS.md`」，并给了 Ghostty 的实例：
  > **那份文件里每一行都对应一次 agent 的错误行为**。本库的 `AGENTS.md` 走的是同一条路，
  > 但**本库从未用这个语汇描述过它** —— 本项目要做的事之一，就是把本库已有的无名实践跟这套新语汇**对一次表**。
  > **2026-09-19 已回填**：该页补上了 OpenAI 素材带来的两条失败模式（**指导过载**与**规则腐坏**），
  > 见其「两条本库此前未评估的失败模式」一节。**本库此前对 `AGENTS.md` 的关切只有「常驻成本」一个维度。**
- **机制层 —— 反馈回路**：[[cybernetic-learning]]、[[wiki-lint]]、[[ingest-query-lint]]
  > [[wiki-lint]] 是 harness 里的 **sensors**：它不阻止错误发生，它让错误**在到达人眼之前暴露**。
  > [[cybernetic-learning]] 给的是理论 —— 「目标 → 误差信号 → 过滤器」与 harness 的 guides / sensors 是同一件事的两种说法。
  > **本项目要验证这个对应是不是真的成立**，而不是顺手拿来当类比。
- **对照层 —— 本库自身的机制**：[[llm-wiki-pattern]]、[[three-layer-architecture]]、[[compounding-knowledge]]、[[rag-vs-wiki]]、[[plain-text-and-git]]
- **元层 —— 本库的证据基础**：[[source-pool-bias]]
  > 本项目自己的调研**已经踩了这个坑**：见缺口表最后两条。这一页是自省工具，不是背景阅读。
- **代价层 —— 个人实践的边界**：[[cognitive-outsourcing]]、[[cognitive-debt]]、[[productive-resistance]]、[[writing-as-thinking]]
  > harness 的代价是**把判断固化进规则**。这几页提供的是反面：外包综合与记忆会让判断力用进废退。
  > **新维度的内部张力在这里**：「高效实践」要求把判断固化成规则（人不必再想），
  > 「深度理解」要求人**仍能看穿那些规则** —— **这两者是不是可以兼得，是第四个维度最硬的问题**，目前没有答案。
  > 乐观读法：harness 把低价值判断自动化，腾出高价值判断；悲观读法：它让人不再需要理解规则为什么存在。
  > 两种读法都能从现有材料里找到支持，**本库必须显式标注这是一处未决**。

## 不做什么（反范围）

- **不做 harness 框架 / 工具横评** —— LangChain、CrewAI、AutoGen 之类不在范围内
- **不写 coding agent 的实现教程** —— 那是 [[traecode-pkm-article]] 的地盘
- **不重复 [[llm-wiki-research]] 的「为什么要建 LLM Wiki」** —— 见决策记录
- **不复述 [[agents-md]] 已覆盖的规则内容** —— 只做「本库实践 ↔ harness 语汇」的对表，不做规则科普
- **不追新** —— 这个领域 2026 年每周都有新文章，本项目只收缺口表点名的
- **不把厂商自述当独立证据** —— OpenAI 那篇的「0 行手写代码」「约 100 万行」「约 1500 PR」等数字，按 [[schema]] §3.4 利益披露处理，`confidence` 降级
- ~~**不在没有反方的情况下动笔**~~ —— **2026-09-19 北洛裁定动笔后，改为有条件放行**：允许在只有支持方的情况下动笔，**但交付物必须单列一节**写明「未找到批评性材料」以及**检索了哪几条渠道**。缺口表第 5 条**保持开着**，不因动笔而关闭。**理由见「决策记录」最后一条。**

- [ ] **「深度理解」与「高效实践」怎么同时成立？** 高效实践要求把判断固化成规则（人不必再想），深度理解要求人**仍能看穿规则**。两者在个人尺度上是否可兼得 —— 这是第四个维度最硬的问题。**2026-09-19 已在 [[harness-explained]] 里作为一节正面处理，但只给出「怎么判断自己偏了」的检验，没给出「两者必然兼得」的结论** —— 保持开着

- [ ] **harness 自己会不会变成新的技术债？** **2026-09-19 有部分材料了**：OpenAI 记录了「一个大 `AGENTS.md`」的四种失败方式，其中 **"It rots instantly"** 正是这个问题的一个实例。**但他们的解法（当目录用 + doc-gardening agent）是团队尺度的** —— 个人没有那个 agent。这一条仍是本项目最实的开放问题
- [ ] harness 与「**规则腐坏**」的关系 —— **2026-09-19 已有材料**（OpenAI 的 "It rots instantly" 与 doc-gardening agent）。**本库自身是这个问题的一个活样本**：`AGENTS.md` / [[schema]] / [[decisions]] 里有大量**特定时点的规则**，而**没有任何机制会告诉维护者哪一条已经过时**。**这可能是一个「本库自己就能贡献一手材料」的缺口** —— 不需要外部文献

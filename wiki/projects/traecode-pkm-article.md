## 当前缺口

> 这一节是控制论里的**误差信号**，也是全页最重要的部分 —— **它决定下一步该找什么素材**。
> 每次 ingest 之前先读这里：这份素材填的是哪个缺口？填不上就不收。

| 缺口 | 卡在哪 | 需要什么素材 / 信息 |
|---|---|---|
| `AGENTS.md` 的加载时机未经一手验证 | 官方文档只讲「如何开启」，不讲「何时加载」；社区说法不统一（缓存说 / 会话启动说）。文章若讲「怎么让规则生效」，这是必答项 | 官方更新日志；或自己实测一轮并记录 |
| `AGENTS.md` 与 `.trae/rules/` 冲突时的优先级未知 | 官方文档未说明，只说了 `#Rule` 优先级最高。文章讲「分工」就必须交代冲突怎么办 | 官方说明；或构造冲突场景实测 |
| 没有「从零开始」的端到端示例 | 本库是长期迭代出来的，不是从空目录走一遍的路径。文章要「可照做」，缺的正是这条真实路径 | 从空目录按自己的说明跑一遍，**记录每一步与踩坑**（这份记录本身也是素材） |
| 「跨 IDE 可复用」只有单方声明 | 目前只有 [[2026-09-18-trae-rules-docs]] 的一句「反之亦然」。这是文章的核心论点，单方声明撑不住 | 其他支持 `AGENTS.md` 的 IDE 的官方说明（Cursor / Claude Code / Codex 等） |
| 本库 `AGENTS.md` 自身太厚（约 18 KB） | 若「常驻成本」成立，拿它当示例等于示范反面做法。但也可能「厚」是被允许的 —— 缺判据 | 他人 `AGENTS.md` 的篇幅实践；或实测常驻开销 |
| 「IDE 维护」vs「Skill 维护」缺独立对照 | [[second-brain-skill]] 是把手册封进工具，本库是把手册放进仓库。这个对比目前只有库内推断 | 一个用 IDE 类工具维护知识库的独立案例 |
| 读者定位未定 | 决定哪些内容展开、哪些略过。**这直接决定缺口表还需要收什么** | 北洛决定（见开放问题） |

## 产出（外向回路）

> 知识库的价值在这里流出。**没有产出的项目是死项目**。

| 产出 | 形态 | 位置 |
|---|---|---|
| 一篇对外文章 | 文章 | **待定 —— 本项目的核心产出** |
| 一个可复现的示例（仓库或模板） | 代码 / 目录 | **待定** —— 决定文章是「讲解」还是「可照做」 |
| 本库自身作为活样本 | 仓库 | `/Users/yongxu/Documents/llm-wiki`（已存在） |

> [!warning] 与 [[llm-wiki-research]] 的关系需要理清
> 两个项目共享同一批知识页，且都以「对外文章」为产出，**存在范围重叠的风险**。
> 目前的分工设想是：
> - [[llm-wiki-research]] —— 研究**模式本身**（从哪来、为什么成立、什么时候不成立）
> - 本项目 —— 讲**怎么落地**（用 TraeCode 一步步搭出来）
>
> 即「为什么」与「怎么做」的分工。**但这条界线尚未经北洛确认**，若两篇文章实际会合成一篇，
> 应把其中一个项目标为 `abandoned` 并记录理由，而不是让两个项目并行漂移。

## 决策记录

> 项目里做过的判断 —— 这是 AI 拿不到的部分，也是本库存在的核心理由。

| 日期 | 决定 | 理由 |
|---|---|---|
| 2026-09-18 | 动笔前先收录 [[traecode]] 的官方规则文档与社区帖 | 文章核心论点依赖「`AGENTS.md` 是否跨工具」，必须有官方依据而非检索印象 |
| 2026-09-18 | 官方文档与社区说法**分页存放**，不合并 | 证据等级不同：前者是规格，后者是未验证实测。合并会污染置信度 |
| 2026-09-18 | 把「本库 `AGENTS.md` 太厚」写进缺口表而非隐藏 | 文章若拿本库当案例，示范的做法必须经得起追问；把弱点写出来比被读者发现更好 |
| 2026-09-18 | 项目阶段设为 `planning` 而非 `active` | goal 的三个关键前提（发表处、读者、是否配示例）未定，此时「开始写」是过早的 |

## 不做什么（反范围）

- 不做 [[traecode]] 的产品评测（不比较它与 Cursor / Windsurf 等的功能优劣）
- 不做通用 PKM 工具选型指南
- 不教编程基础
- 不复述 [[pkm-history]] 已经覆盖的历史线 —— 需要时链接过去，不重写
- 不追求「收录更多 TraeCode 文档」—— 只收缺口表里点名的

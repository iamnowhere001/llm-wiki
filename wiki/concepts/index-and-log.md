# 索引与日志：index.md 与 log.md

> wiki 里两个承担导航职责的特殊文件：`index.md` 面向内容（有什么页），`log.md` 面向时间（发生过什么）。它们让 wiki 在增长后仍然可被 LLM 和人类快速定位。

## 要点

- `index.md`：全库目录，按分类组织，每条 = 链接 + 一行摘要。**每次 ingest 后更新。**
- `log.md`：只追加、不改写的操作时间线，类型有 ingest / query / lint / edit / init。
- 日志用固定前缀 `## [YYYY-MM-DD] type | 标题`，从而可以用 `grep` 解析。
- 查询时**先读 index 再深入页面** —— 中等规模下这比向量检索更可靠。
- 两者都由脚本可重建，但日志是**追加式**的，不能重建。

## 定义与背景

| 文件 | 取向 | 写入方式 | 用途 |
|---|---|---|---|
| `index.md` | 内容 | 每次 ingest 后重写 | 定位候选页 |
| `log.md` | 时间 | 只追加 | 理解最近做了什么 |

作者给出的实用技巧：因为前缀一致，

```bash
grep "^## \[" wiki/log.md | tail -5
```

就能拿到最近 5 条操作记录。

## 机制 / 原理

**为什么索引能替代向量检索。** 在 ~100 份素材、数百页的规模下，让 LLM 先读一份结构化的目录、再决定深入哪几页，效果出奇地好。原因是：目录页本身已经是**人工/LLM 压缩过的语义摘要**，比把文档切块做嵌入更接近「检索意图」。这也避免了维护嵌入索引的基础设施成本。

**为什么日志有用。** 它有两个读者。人类读它是为了回顾知识库的演化；LLM 读它是为了理解「最近做过什么」—— 这在跨会话时尤其重要，因为 LLM 每次都是冷启动。日志相当于给 LLM 的一段短期记忆。

**为什么日志必须 append-only。** 一旦允许改写，就无法信任它。日志的价值来自它是**不可篡改的历史记录**，而不是一份需要保持最新的文档。

## 边界与反例

- **索引会随规模失效。** 当页面数进入数千量级，`index.md` 本身太长，LLM 读它会消耗大量上下文。此时需要真正的检索工具，见 [[qmd]]。
- **索引不是数据源。** 它必须能从各页 frontmatter 重新生成。本项目用 `python3 tools/wiki.py index` 做这件事。
- **日志不记流水账。** 只有有长期价值的操作才值得记，否则会稀释信号。

## 与其他页面的关系

- 服务于 [[ingest-query-lint]] 的每一步。
- 索引的失效边界指向 [[qmd]]。
- 本仓库实例：`wiki/index.md`、`wiki/log.md`。

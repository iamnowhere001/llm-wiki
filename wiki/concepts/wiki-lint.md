# Wiki 体检（Lint）

> 定期让 LLM 检查知识库的健康状况。它既修问题，也**生产下一步的选题** —— 这是 [[llm-wiki-pattern]] 对抗熵增的机制。

## 要点

- 检查项分两类：**机器可查**（断链、孤岛、缺 frontmatter）与**语义可查**（矛盾、过期、该建未建）。
- 最有价值的产出往往不是「修了什么」，而是「**接下来该读什么、该问什么**」。
- 每次 lint 都应写入 `log.md`，形成维护节律。
- 语义检查必须由 LLM 做阅读理解，脚本无法替代。

## 定义与背景

作者列出的检查项：

| 类别 | 检查项 | 谁来做 |
|---|---|---|
| 结构 | 断链（`[[x]]` 指向不存在的页） | 脚本 |
| 结构 | 孤岛页（无入链） | 脚本 |
| 结构 | 缺少 frontmatter / slug 与文件名不一致 | 脚本 |
| 语义 | 页面之间的矛盾 | LLM |
| 语义 | 被新素材推翻的过期论断 | LLM |
| 语义 | 被反复提及但没有独立页的概念 | LLM |
| 语义 | 缺失的交叉引用 | LLM |
| 增长 | 可以用一次网络搜索补上的数据缺口 | LLM |

## 机制 / 原理

**为什么语义检查不能脚本化。** 「两页矛盾」需要理解两段自然语言说的是同一件事但结论不同；「过期」需要判断新素材是否真的推翻了旧论断；「该建未建」需要判断一个名词是否已经重要到值得独立成页。这些判断依赖语义理解。

**为什么 lint 是选题引擎。** 检查过程中会自然浮现两类信息：知识库里反复出现但缺乏来源的概念 → 说明该去找哪方面的素材；两个页面之间的空白 → 说明该问什么问题。作者明确说「LLM 很擅长建议新的问题和新的素材方向」。

**检查阈值的设计。** 页面类型不同，标准不同。`sources/` 页面不需要出链（它是端点），但必须有入链；`concepts/` 和 `entities/` 必须既有入链又有出链，否则说明它没被整合进网络。本项目在 [[index-and-log]] 之外的 `tools/wiki.py lint` 中实现了这套阈值。

### 非标准检查：HFQ（2026-09-18 新增）

`sources/` 的结构性检查之外，本库还检查**每份素材页里人类亲笔留下的痕迹**：

| 检查 | 判据 | 报告级别 |
|---|---|---|
| **HFQ**（人类先问，`AGENTS.md` 4.1 第 −1 步） | `source` 页是否有 `## 人类先问` 节、且节内不含「待人类亲笔」占位 | **语义提示，不计入问题数** |

**为什么不计入问题数**：该条款 2026-09-18 才裁定，存量素材按过渡期说明不追补，
所以「缺这一节」在存量上是预期内的。**真正的信号是「已建节但没填」** ——
那说明有一份素材在等人亲笔。**它是一条待办，不是一处缺陷**，所以 `lint` 把它单列出来。

**它与其它检查的区别**：所有既有检查都在问「库里的内容对不对」；
**这一条在问「库里的问题是谁提的」** —— 见 [[cybernetic-learning]] 的过滤器链。

## 边界与反例

- **不要 lint 一建就做。** 十页规模时检查没有信息量。
- **不要为了指标而建页。** 如果为了消除「该建未建」告警而给每个名词建一个空壳页，wiki 会变成噪音。
- **孤岛告警要考虑 index 的链接。** `index.md` 链接了所有页面，如果把它算作入链，就永远不会有孤岛告警。本项目在计算时忽略来自 `index.md` 的入链。

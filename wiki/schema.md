## 1. 页面规范

### 1.1 Frontmatter（每页必需）

```yaml
---
title: 页面标题
type: concept            # source | entity | concept | analysis | project | meta
slug: llm-wiki-pattern   # 全库唯一，与文件名一致（不含 .md）
tags: [知识管理, 模式, LLM]
created: 2026-09-18
updated: 2026-09-18
sources: [2026-09-18-karpathy-llm-wiki]   # 支撑本页的 raw 素材 slug
related: [rag-vs-wiki, ingest-query-lint] # 相关页面 slug
evidence_tier: single    # single | crossed | primary —— 见 1.2
confidence: high         # high | medium | low —— 证据充分度（主观判断）
status: active           # active | draft | stale | deprecated
---
```

**`slug` 必须与文件名一致**，且全库唯一。工具链靠它解析链接。

`meta` 与 `project` 页不需要 `sources` / `evidence_tier`：前者是系统文件，后者的来源是「我要做什么」而非某份素材（`lint` 已豁免）。

### 1.2 `evidence_tier`：这页的结论站得多稳

`confidence` 是 LLM 的**主观**判断，会随阅读而变，机器校验不了。
`evidence_tier` 是**可计算的事实** —— 由 `sources` 列出的素材数量与类型推导，`lint` 会校验它与事实是否一致。
**两者是两个维度，不要互相替代。**

| 取值 | 判据 | 意味着 |
|---|---|---|
| `single` | 恰好 1 份支撑素材 | **孤证**。引用时必须带着「只有一份来源」这个前提 |
| `crossed` | ≥2 份支撑素材，且不含一手文献 | 交叉了 —— 但**可能只是同源转述**（见下） |
| `primary` | ≥1 份 `kind: paper` 的素材支撑 | 有可独立核验的一手文献 |

> [!warning] 「名义交叉，实质同源」是本库最大的陷阱
> 多份素材不等于多个独立佐证 —— 本库有 **70 份素材同属一个来源族**（同一套得到课程的讲稿、问答与整理笔记）。
> `lint` 会报出「有 ≥2 份支撑但全部来自同一来源族」的页面 —— **那些页面不能当作已交叉验证**。
> **归并失败时默认「各自独立」，不并族** —— 把真交叉误判成同源，比漏报同源代价更大。

**写入方式**：`tools/seed_evidence_tier.py`（幂等）。填错了 `lint` 会报。

> [!note] `primary` 的三个边界（裁定理由见 [[decisions]]）
> - **`primary` 不是「证据强度排名」，是「有没有期刊论文级一手材料」这一个事实。** 一手专著会停在 `crossed` —— 这不是低估，是字段管不了这件事。
> - **补救不在字段里，在正文里**：这类素材的 `sources/` 页与它支撑的知识页，**必须用文字显式写明「本页有一手专著 / 作者一手文本支撑」**。`lint` 与 `evidence_tier` 都不会替你说这句话。
> - `primary` 页也未必比 `crossed` 页可信（论文本身可能质量差）。**两个维度始终独立。**
>
> **`evidence_tier` 已由 frontmatter 表达，正文里不再插警示块。**

### 1.3 页面类型

| type | 目录 | 一页是什么 | 何时创建 |
|---|---|---|---|
| `project` | `projects/` | **我在做的一件事**：目标、当前缺口、消耗的知识、产出 | 人类提出一个要推进的目标 |
| `source` | `sources/` | 一份素材的结构化摘要 | 每次 ingest |
| `entity` | `entities/` | 一个具体的人 / 组织 / 工具 / 产品 | 素材中反复出现的具名对象 |
| `concept` | `concepts/` | 一个抽象的理论 / 方法 / 模式 / 术语 | 素材中反复出现的抽象概念 |
| `analysis` | `analyses/` | 一次对比 / 综述 / 回答归档 | 有价值的问题答案、跨页综合 |
| `meta` | `wiki/` 根 | index / log / overview / conventions / schema / decisions | 系统文件 |

**判定规则**：能被指着一张照片说「这是它」的 → entity；只能被描述、不能被拍照的 → concept。

**创建阈值**：一个名字在 ≥2 份素材中出现，或者在一份素材里是核心论点 → 独立成页。只出现一次的次要名词，先在正文里提一句，等它再次出现再建页。

### 1.4 正文结构

每个页面遵循「**先结论，后细节**」。**具体骨架以 `templates/` 为准** —— 五类页面各有模板，`python3 tools/wiki.py new <type> <slug>` 照它生成。

**所有类型共通的四条**：

1. **页首一句提要** —— 读者只看这一行也能知道这页在讲什么。
2. **收尾节统一叫 `## 待办 / 开放问题`** —— 内容是该页已知的未解问题（`- [ ]` 清单）。
3. **`## 来源` 收尾** —— 知识页指向支撑素材；source 页指向自己（自指）。
4. **至少 1 条出链、1 条入链**（`sources/` 例外）—— 见 §1.5。

**模板体检**：`python3 tools/wiki.py template-check` —— 核 `templates/*.md` 与 `wiki.py` 内联兜底模板是否逐字节一致、五类模板结构是否合规。有问题返回非零。

**关系节只有一个名字：`## 与其他页面的关系`**（2026-09-21 全库归一，此前有四个同义异名）。

### 1.5 链接语法

- 页内链接：`[[slug]]` 或 `[[slug|显示文本]]`
- **只链接已存在的页面。** `[[x]]` 指向不存在的页，lint 会报 broken link。
- 每页至少 **1 条出链**（除 `sources/` 外）和 **1 条入链**。孤立页会被 lint 标出。

### 1.6 项目页（入口层）

项目页回答的不是「这是什么」，而是**「我在做什么、因此什么重要」**。依据来自 [[cybernetic-learning]]：

```
目标 → 误差信号 → 过滤器 → 相关性 → 留存
```

没有目标，就没有误差信号；没有误差信号，大脑不会标记什么重要。**项目页就是把「目标」和「误差信号」显式写下来的地方。**

#### frontmatter

```yaml
---
title: 项目名
type: project
slug: project-slug
tags: []
created: 2026-09-18
updated: 2026-09-18
goal: 一句话目标，要能被判断「完成没有」   # 项目页特有，必填
stage: planning                          # 项目页特有
started: 2026-09-18
sources: []      # 项目通常留空 —— 它的来源是意图，不是素材
related: []
confidence: high
status: active
---
```

**`stage` 与 `status` 是两个维度，不要混用：**

| 字段 | 回答的问题 | 取值 |
|---|---|---|
| `status` | 这**页**还新鲜吗 | `active` / `draft` / `stale` / `deprecated` |
| `stage` | 这**事**做到哪了 | `planning` / `active` / `paused` / `shipped` / `abandoned` |

**`goal` 必须可验收** —— 判据是「看到 goal 能回答『做完了没有』」。不能验收的目标产生不了误差信号，等于没写。

#### 正文结构与作用

| 小节 | 作用 |
|---|---|
| 目标（可验收） | 参考信号 |
| **当前缺口** | **误差信号** —— 全页最重要的一节 |
| 知识 | 本项目消耗哪些页面 |
| 产出 | 外向回路 —— 知识流出到哪里 |
| 决策记录 | 项目里做过的判断（AI 拿不到的部分） |
| 不做什么 | 反范围，避免蔓延 |

**「当前缺口」是项目页存在的核心理由。** 必须写成表格：`缺口 / 卡在哪 / 需要什么素材`。表格保持三列；需标优先级时在「缺口」列内用 `**【阻塞】**` 前缀。

**缺口表有两类条目，不要混：**

| 类 | 形态 | 含义 |
|---|---|---|
| **文献缺口**（默认） | 「知道缺什么，卡在哪，需要什么素材」 | **有来源提示过这里有洞** |
| **未知缺口** | 「本库不知道这里缺什么，因为**没有任何来源提示过**」 | **洞本身是不可见的** |

「未知缺口」与 §4.1「说『库里没有 X』前必须先检索」**同型** —— 都是把「不知道」变成需要举证的状态。

**判据**：一个项目的缺口表里如果**全部**是文献缺口，大概率没做过偏差分析。

「未知缺口」的第三列**不指定具体素材**，而写**什么机制能让这个洞变得可见**。

> [!warning] 「未知缺口」不能当通行证 —— 它不满足「填得上缺口」的检验
> `AGENTS.md` §3 第 7 条要求「收录前先读缺口表，填不上任何缺口的素材现在还不该收」。
> **一条「未知缺口」不构成「填得上」** —— 否则任何素材都能声称自己在填它，这条前置检查立即失效。
> 声称在填「未知缺口」时，必须说明**这份素材如何把那个洞变得可见**。
> **「未知缺口」的用途是「说明为什么收不到」，不是「放行任意素材」。**

#### 生命周期

- 项目 `shipped` 后**不删除**。它的「决策记录」是后续项目最值钱的参照。
- `abandoned` 时在「决策记录」里写清**为什么放弃** —— 这比成功记录更稀缺。
- 长期 `paused` 且无产出，考虑降级为 `analyses/` 里的一页，或标 `abandoned`。

**终点判据：缺口表清空即 `shipped`。** 决定不做的缺口**移入「不做什么」**，否则表永远清不空。

| 情形 | 处理 |
|---|---|
| 新素材填的是**现有缺口** | 正常 ingest，项目仍 `active` |
| 已 shipped 后，新素材开的是**新缺口** | **另开一个项目**，原项目保持 `shipped`，不复活 |
| shipped 后，新素材**推翻了原项目结论** | **原项目复活**：`stage: shipped → active`，决策记录写明哪条结论被推翻 |

> [!warning] 「另开一个」必须防的退化
> **另开项目 ≠ 从零开始。** 后继项目**必须显式继承前任**：决策记录里引用前任 slug、缺口表标明哪些是继承的、把前任被否决的方案与伦理风险重申一次。完整理由见 [[decisions]]。

### 1.7 标签规范

`tags` 是**导航字段**，不是关键词堆。它只有一个用途：**让同一主题的页面在侧栏、索引与标签面板里聚到一起**。

**判据 —— 把标签念成一句话：**

| 念成 | 判 | 例 |
|---|---|---|
| 「这页讲 **＿**」 | **保留**（主题） | `认知科学` `决策` `心流` |
| 「这页属于 **＿**」 | **保留**（系列归属） | `现代思维工具` `成长战略` |
| 「这页出自 **＿** ／ 是 **＿** 说的」 | **保留**（署名） | `万维钢` `塔勒布` `孔子` |
| 「**＿** 是谁」 | **保留**（角色） | `人物` `研究者` |
| 「这页 **是** ＿」 | **移除** | `素材` `纯讲稿` `一手文献` `AI生成` `待裁定` |

最后一行是全部规则：**`tags` 里不出现「关于这一页自己的属性」。** 素材形态、核查状态、生成方式、抓取与组织元数据 —— 四类都属此列。

> [!note] 署名是转述者，不是提出者（2026-09-20 二次裁定，理由见 [[decisions]]）
> `万维钢` 是转述者；库里大量概念的提出者是霍林、塔勒布、古德哈特。
> 署名标签只记「这页出自谁」，**不区分「谁提出」与「谁转述」** —— **要表达「谁提出」，靠实体页与正文，不靠标签。**

**移除集只有一份**：`tools/tags_vocab.py` 的 `REMOVE`。`lint` 报出落在移除集内的标签，检查名 `标签属于移除集`。
**本规则没有频次门槛** —— 门槛会把只出现一页的署名与主题词一并删掉，而「只出现一次」恰恰是署名与专题词的常态。

**顺序**：顶栏按 **系列 → 署名 → 主题** 排，组内按全库频次降序。
**标签不再承担导航职责** —— 标签是交叉的，分类要求互斥，两者结构上不兼容（[[decisions]]「侧栏去掉二级分组」）。

**新增词条**：改 `tools/tags_vocab.py` 并同步本节；改完跑 `lint` 复核。

### 1.8 source 页的正文区与账目区

浏览站点是一份**给读者看的视图**。一页 source 的自然形状是**三段**：

| 段 | 内容 | 站点侧怎么渲染 |
|---|---|---|
| 上款 | 标题 / 提要 / 出处卡（作者 · 链接 · 发表 · 素材路径） | 提要 → 独立面板；元信息行 → 出处卡 |
| 正文 | 关键要点 / 摘要 / 与本库的关系 / 新出现的实体 / 待办 / 相关页面 | 直接展示 |
| 账目 | 分层表 / 引注核查表 / 回填清单 / 归属判断 / 定级理由 / 证据性质 / AI 加工段判定 | **折叠成卡片，默认收起**（文字一个不删） |

**为什么区分**：读者打开一页想知道「这份素材讲了什么」，不该先翻过等量的记账。归到账目区**不代表它不重要**，只代表**读内容的人不需要它**。

**判定词表是唯一真源**：`tools/wiki.py` 的 `READ_EXACT` / `READ_H2` / `LEDGER_H2`。`build` 时注入站点、`chapter-audit` 直接读同一份 —— **不要在别处另抄一份**。
判定顺序 = 精确名 → 正文字串 → 账目子串 → **默认正文**。兜底偏保守是故意的：误折一个正文章节（读者会以为库里没这段）比漏折一个账目章节代价大得多。

```bash
python3 tools/wiki.py chapter-audit       # 只读对账：每页折了多少、哪些章节名落在词表之外
python3 tools/wiki.py chapter-audit -v    # 逐页
```

> [!warning] **不做批量改名，也不做自动重排**
> 本库有大量页内指向引用（见下 / 见上 / 下文 / 上表 / 本节 …）与指名引用。**这类引用没有机器兜底**，改章节名或把账目统一搬到页尾，都会让它们指空而没人发现。
> 因此站点把「账目置底」做成读者自己按的开关（页内 `#ledgctl`），不是默认行为。
> 同义异名由 `chapter-audit` 列出来，**改不改由人裁定**。

**出处卡收敛为 4 项**：`作者` / `链接` / `发表` / `素材路径`。

- 元信息取自 **raw 文件的 frontmatter**（`author` / `url` / `source_url` / `published`），**不从页面正文里猜**。
- 多个链接并作一行，用 ` ｜ ` 分隔；**值不是 URL 的不并入**（归账目区）。
- **账目类字段一律不进出处卡**：`性质` / `讲次` / `编号依据` → `## 归属判断`；`证据层级` / `采集质量` → `## 定级理由`；`内嵌资源` / 图片 `file_token` 对照表 → `## 素材分层表`（无该节则 `## 已知缺失`）。
- **`抓取` 与 `行号坐标系` 一类不写进 source 页** —— 它们在 raw frontmatter 的 `capture_method` / `capture_note` 里，在 wiki 页抄第二遍就是冗余。

**已取消的章节**：`## 素材基本信息`（见 [[decisions]]）。它的内容逐条都在 raw frontmatter 与出处卡里，写进 source 页是同一件事的第三遍。

**新页从 `templates/source.md` 起手** —— 它已经把上款、正文区、账目区、页脚排好了。

## 2. 收录

人类把素材丢进 `raw/`，然后说「收录」。**ingest 没有任何人类前置条件**（原「第 −1 步：人类先问」已于 2026-09-18 废止，墓碑见 [[decisions]]）。

**第 0 步：读 `wiki/projects/`。** 判断这份素材服务于哪个项目的哪个缺口。

- 能对上 → 在 `sources/` 页里写明「服务于 `[[项目slug]]` 的哪个缺口」，并在项目页的「知识」一节加回链。
- 对不上任何缺口 → **先向人类指出**：「这份素材填不上任何当前缺口，确定要收吗？」

然后按顺序执行：

1. **抓取**：质量要求见 §3。落盘后校验一次链接是否还在。
2. **读**：完整读一遍素材，含 frontmatter。引用图片的素材，先读文本，再单独查看关键图片。
3. **对齐**：向人类汇报 3-5 条关键要点，以及它与现有 wiki 的关系（新增？印证？**矛盾**？）。冲突时**明确指出，不要悄悄覆盖**。
4. **核查** —— **L0 事实核查每次收录都做；L1 全文校准命中触发条件才做**（§3.8）。
   - **链接可信时的正确动作**：读链接指向的那一段、确认它**说了那句话** —— 而不是确认链接**能打开**。后者正是 §3.6「伪引注」最常伪装的形式。
   - **核不到就如实写「未找到」或（未验证）** —— 「核过而没有」本身就是信息。
5. **（条件性）反方检索** —— **AI 生成占比 > 60% 的素材，收录时必须跑一次反方检索。**
   - 这类素材最可能缺的正是反方 —— AI 倾向于给共识不给争议（见 [[source-pool-bias]] 第三节第 ③ 条）。
   - 结果写进「反方与失败条件」一节。**检索不到就写「未找到」，不要留空。**
   - **不溯及既往**：只管新收录；已入库的高占比素材在下一轮 L1 校准时顺带处理。
6. **写摘要页**：`wiki/sources/<slug>.md`，按模板。slug 取 `YYYY-MM-DD-短标题`。
7. **拆实体 / 概念页**：按 §1.3 的阈值，新建或更新 `entities/`、`concepts/`。
8. **回填**：更新所有被影响的已有页面 —— 补充事实、修订结论、标注矛盾。
   **一份素材通常触及 10-15 个页面，只写摘要页是失败的做法。**
9. **更新索引**：在 `wiki/index.md` 对应分类下加入新页与一行摘要。
10. **写日志**：`python3 tools/wiki.py log ingest "素材标题"`。
11. **自查**：`python3 tools/wiki.py lint`，确保无 broken link。
12. **（条件性）构建站点**：只在里程碑时 —— 判据见 §2.1。

### 2.1 构建时机 —— 只在里程碑时

`site/index.html` 是**构建产物**：把 `wiki/` 下全部页面连正文内联成一个单文件，供浏览与分享。**它不是文档，是视图** —— 不与 `index.md` / `log.md` 同级、不需要每次更新。

**判据（满足任意一条即是）：**

| # | 触发条件 | 为什么算里程碑 |
|---|---|---|
| 1 | **新增一条主线** | 「这个库在讲什么」变了 |
| 2 | **新增或关闭一个项目** | 入口层变了 |
| 3 | **自上次构建以来，更新页面 > 5，或新建页面 > 3** | 站点的**正文**有可见变化 |
| 4 | **一次大 ingest 收尾** —— 整系列收录、多份素材同批、或一份素材派生 ≥5 个新页 | 单次改动量大 |
| 5 | 人类明确要求 | —— |

**不命中的改动（单页回填、修笔误、补一条待办、调整 `related`）一律不构建。**

**判据 3 怎么核**：`python3 tools/wiki.py buildcheck` —— 拿 `site/.build-manifest.json`（`build` 时自动写，每页一条内容指纹）与当前 `wiki/` 逐页对比，直接给判定。

- **「更新页面」**＝基准里有、内容指纹变了的页数；**「新建页面」**＝基准里没有的页数。两者都与页面总数无关。
- **排除 `index` 与 `log`** —— 它们每次都变，且变化是别的改动的后果，计入会把阈值架空。
- **`site/.build-manifest.json` 不存在时 `buildcheck` 返回非零** —— **不要把它读成「判据 3 不命中」**；没有基准时按判据 1/2/4/5 走。

> [!warning] 没有任何机制会发现站点落后
> `lint` 只管 `wiki/` 下的 Markdown；`site/` 不在任何检查的覆盖范围内。
> 因此本条的落地方式不是「记得构建」，而是「**照上表逐条判断**」：有命中就构建，**都不命中就明确地不构建**。
> **「明确地不构建」与「忘了构建」在结果上一样，在过程上不同** —— 前者可审计，后者是事故。

**构建后**在 `wiki/log.md` 记一条 `edit`，写明上次构建时间与本次跨越了几次改动（可照抄 `buildcheck` 输出）。**这条记录是日后判断「站点还可不可信」的唯一依据。**

> [!note] 与「更新索引」的区别
> `index.md` 是**知识库的组成部分**（查询第一站），**必须每次更新**；`site/index.html` 是**导出快照**，**允许滞后**。

## 3. 抓取质量与证据问题

### 3.1 质量优先于速度

网页正文抓取会丢行内链接、把 `→` 转成 `->`、丢表格分隔符。**只要目标提供结构化端点，就用它**：

- GitHub 仓库 → `api.github.com/repos/<owner>/<repo>`（元数据）+ `/readme`（正文）
- Gist → `gist.githubusercontent.com/<user>/<id>/raw`
- X / Twitter → `cdn.syndication.twimg.com/tweet-result?id=<id>&token=a`
- 飞书云文档 → `lark-cli docs +fetch --doc-format markdown --as user`
- 静态文档站 → 直接取 `.md` 源文件而非渲染后的 HTML

落盘后**校验一次**：正文里应该有链接的地方是否还有链接。

**若只能用 AI 中介的抓取工具，必须交叉验证** —— 用独立元数据源比对，并在 `capture_quality` / `capture_note` 中如实记录可信度与已知缺失。

### 3.2 抓取元数据例外（清理历史遗留专用）

**这不是常态化的可写权限。** `raw/` 不可变是铁律，本条只用于清理**历史遗留的错误元数据**。

**准入条件（必须全部满足）：**

1. **只限 frontmatter，正文一字不可改。** 正文抓取有误 → 走 `-r2` 重抓流程。
2. **只限「本库自产的描述性字段」** —— 白名单：`capture_note` / `capture_quality` / `capture_method` / `clipped` / 抓取标识 / `assets`。
   **黑名单（绝不可改）**：`title` / `author` / `url` / `published` / `kind` —— 改它们等于篡改来源标识。
3. **必须由人类裁定。LLM 不得自行修改。** LLM 只能提出更正请求并附证据（行号 + 该行实际内容）。
4. **不得覆盖，只能追加。** **「可更正」≠「可覆盖」** —— 允许覆盖就等于允许消灭证据。
5. **优先「移除」而不是「改正」。** 若某字段的数据本身就是错的（典型是行区间），**整段删掉、改为指向 `sources/` 页的指针** —— 指针不会错。
6. **改动必须同时做三件事**：`log.md` 记一条；对应 `sources/` 页写明「raw 元数据于 X 日更正，原值 Y，依据 Z」；**扫描并更正所有下游引用**。
7. **一次只改一个字段**，改完立即 `lint`。
8. **尽量用等行数替换。** 无法避免时必须重新测量全部区间并按第 6 条同步下游。

### 3.3 全库默认文件绝对行号，页内不再声明坐标系

**规则**：引用 `raw/` 一律用**文件绝对行号**（`wc -l` 坐标系），**页内不写坐标系声明**。
写「行 165–175」之前，回文件 `sed -n '165,175p'` 看一眼。**凭记忆沿用行号是本库已犯过三次的错。**

**例外**：**偏离默认的才要写。** 若某页用的不是文件行号（例如 PDF 阅读器页码与纸质版页码不同），必须写明 —— 读者无从推断。

**怎么识别旧数据用的坐标系**：若 `capture_method` 里记的「正文 N 行」**小于** `wc -l` 的实际行数，那 N 就是内容相对行数，差值即 frontmatter 长度。

**核法**：`lint` 报「行号坐标系残留声明（sources / concepts）」。它只拦**声明式**写法；**讲历史**与**讲另一种坐标系**（页码、两份素材的行号区分）不算违规。
（sources 页 2026-09-20 取消，concepts 页 2026-09-21 取消 —— 同一次清理里顺手改了 `lint` 的覆盖面，否则这批统一是一次性的。）

### 3.4 利益披露

**素材含推广内容时必须标注**（作者是产品运营者、带 UTM 链接等）：在 frontmatter 与摘要页写明，并把相关页面的 `confidence` 降级。

### 3.5 AI 生成内容

| 步骤 | 要求 |
|---|---|
| 收录 | **收** —— 它作为「对照样本」有价值，示范了「结构完整度 ≠ 证据强度」 |
| 定级 | **按内容质量定，不按「是不是 AI 生成的」定** |
| 引用 | **可以引用，但必须标注其 AI 生成性质与 `confidence`** |
| 说明 | frontmatter 写明 `kind` 与收录理由；摘要页写明低置信度的原因与仍收录的原因 |

**为什么不禁止引用**：完全禁止会让这类素材无法参与库内论证，而降级 + 标注保留了它作为反例的功能。

**区别于「推广内容」**：推广内容的问题是可追溯性（能追溯但动机有偏），AI 生成内容的问题是可追溯性为零。

**判据的判据** —— 问一句：**「这段话如果错了，读者能不能自己发现？」** 能（有链接 / 可试用 / 显式「未验证」）→ 保留 `confidence`；不能 → 降级。
**降级的是行为，不是作者身份。**

### 3.6 证据问题分六类

**处理方式不同，不要混为一谈。**

| 类别 | 问题性质 | 处理方式 |
|---|---|---|
| 推广内容 | **可追溯，但动机有偏** | 标注利益披露 + 相关页降级 |
| 纯 AI 生成 | **可追溯性为零** | 按内容质量定级（§3.5） |
| **伪引注** | **可追溯性被伪造** —— 精确数字配模糊归属 | 整页降级 + **区分「不可追溯」（判断）与「已核实不存在」（事实）** |
| **弱引注** | **可追溯性被放弃** —— 精确数字配「有研究表明」 | **逐条标「（未验证）」**，不整页降级 |
| **引注的使用失真** | **可追溯性完好，但数字/结论的对应关系被搞错** | **逐条公示「素材说 X ↔ 原文说 Y」**，不整页降级 |
| **过期引注** | **引注真实、对应关系也对，但结论已被后来的研究推翻** | **逐条标「（已过期）」+ 写明推翻它的研究**，不整页降级 |

**前三类是「污染」，后三类不是。** 混同会让「引注不规范」看起来像「学术不端」；反过来，把伪造当成不规范，则会放过更严重的问题。

**伪引注最危险**：前两类看署名就能警觉，伪引注要真去查才发现查不到。

**后三类的识别方法各不相同，第一步都不是「查有没有出处」**：使用失真要核对**对应关系**；过期引注要核对**该研究的当前状态**（后续复现 / 元分析 / 作者撤回）。

### 3.6.1 「过期引注」的边界与判法

**它为什么不与前三类同列**：引注是真的、数字是真的、位置也对 —— **素材没有骗人**。问题出在**时效**。

| 容易混的类 | 区别 |
|---|---|
| **弱引注** | 弱引注是**没给出处**；过期引注是**出处给了、也是对的，只是过时了** |
| **引注的使用失真** | 使用失真是**数字安错了位置**；过期引注是**位置没错，结论本身失效了** |
| **伪引注** | 伪引注是**查不到**；过期引注是**查得到、而且真实** |

**升格判据**：**若素材写于结论被推翻之后，却仍按既定事实陈述，则不算「过期」，而是「明知故用」** —— 更接近使用失真，甚至更重。

**连带影响 `confidence`**：若一页的**核心断言**依赖过期引注，该页 `confidence` 须降 —— `evidence_tier` 管不了时效。

**这类核查是持续性的，不是一次性动作。** 库内已登记的候选见 [[decisions]]。

### 3.7 混层素材必须逐行比对数字

一份素材内部常混层（逐字引文 / 讲稿 / AI 阐释 / AI 报告并存）。AI 生成的摘要段会「**补进**」原文没有的具体数字 —— **但不总是**：有的做**加法**，有的做**减法**。
**同一来源、同一形态的两份笔记，摘要段的行为可以完全相反。因此不能按形态一刀切，只能逐份逐行核对。**

> [!warning] 判「加法」需要一手对照
> **在素材内部检索，无法区分「素材里没有」与「原书里没有」。**
> 只有素材内部比对时，**只能说「该数字未在正文段出现」，不能说「它是 AI 补的」**。本库曾把一次「减法」误判成「加法」（见 [[decisions]]）。

**另注意区分三种缺陷，不要合并**：
- **「书里没有」**（素材编造）
- **「书里有但无引注」**（证据强度不足）
- **「书里有，但素材没节选到」**（**节选的完整性**问题 —— 判这一条**必须有一手全文**）

单一 `confidence` 不够，`sources/` 页要加**分层表**（段 / 行区间 / 性质 / 署名 / 置信度）。

### 3.8 核查分两级：L0 事实核查 / L1 全文校准

**本条取代「每份素材必经一手校准」的旧做法。**

| 核查目的 | 级别 | 需要什么 | AI 核片段够不够 | 收原文？ |
|---|---|---|---|---|
| **A. 这句话是不是真的**（数字 / 署名 / 引文） | **L0 事实核查** | 该断言出现的那一段 | **够** | **不必收** |
| **B. 这份素材少了什么 / 有没有把话说圆** | **L1 全文校准** | 一手**全文** | **不够** | 必须收 |

> [!note] B 为什么不能用片段做
> 依据是 §3.7：**在素材内部检索，无法区分「素材里没有」与「原书里没有」。**
> 片段核查**只能证真、不能证伪**，还会把「遗漏」误判成「编造」。

**L0（每次收录都做）**：对**带数字、带引号、带署名**的断言逐条核出处。
核的是「**这个片段里有没有这个断言**」，不是「**链接能不能打开**」。核不到就写「未找到」或（未验证）。

**L1（命中任一触发条件才做）**：

| # | 触发条件 | 为什么 |
|---|---|---|
| 1 | **原文已在库**（`assets/` 有对应 PDF） | 零获取成本 |
| 2 | **该素材 / 该页的断言被下游引用 ≥3 处** | 传播面大，错了要回填多处 |
| 3 | **已出现具体怀疑**（数字对不上 / 引号内查不到 / 署名含糊） | 已有误差信号 |

- **都不命中 → 只做 L0**，并在该页正文写一句「本页未做全文校准」。⚠️ **这句不设 frontmatter 固定字段** —— 它是正文里的一句话，加了会让 `lint` 与 `seed_evidence_tier.py` 误以为它参与证据计算。
- **不要攒到项目 `shipped` 前一次性清算**：一手校准不是缺口驱动的，攒着做是把成本从线性变成爆发。

**L1 的三个专查动作**：**核数字**（含**适用范围** —— 凡「A 与 B 都……」式并列断言，必须分别核 A、B 各自的数字）／**术语表核对 + 同形异义检查**／**核归属**（凡出现「某人提出了 X」，都要问「署名核过没有」）。

### 3.9 判「矛盾」前先问两侧命题在不在同一层

> **同一术语 + 相反符号，只是矛盾的「候选条件」，不是充分条件。**
> 登记一处矛盾之前，必须先问：**两侧说的命题，在不在同一层？**
> 若两侧分别在「怎么设计」与「谁来发起」这类不同的层上，它们**不是矛盾，而是互为条件**。

**为什么需要这条**：本库曾把 [[cognitive-load-theory]]（负荷是**负债**、要管住）与 [[2026-09-18-active-cognitive-load-notes]]（负荷是**目标**、要加满）判为「真矛盾」，后来裁定作废 —— 原判据**只比了符号，没比命题所在的层**：一侧说**怎么设计**（工程化），一侧说**谁发起**（主动性），两者**互为条件**。

**边界：什么才算真矛盾。**

| 形态 | 判据 |
|---|---|
| **两个维度、互为条件** | 一侧说「谁来做」，另一侧说「怎么做」 |
| **同一侧**（措辞相反、主张相同） | 两人反对的是同一样东西 |
| **切分框架不同** | 两侧切的范围不同 |
| **真矛盾** | **同一维度、同一命题、相反断言** —— **本库目前无实例** |

> [!warning] 取消「矛盾」归类 ≠ 两条进路都无效
> 判为「两个维度」之后，**两条进路仍然各自成立、仍然要分别执行** —— 改归类是为了让读者知道**两个都能做**。

**连带影响 `confidence`**：若一页 `confidence` 偏低的首要理由是「存在未裁决的矛盾」，裁定后**值不必变、但理由必须重写**。理由变了而值不变，也要显式写出来。

## 4. 查询

1. 先读 `wiki/index.md` 定位候选页（中等规模下比向量检索更可靠）。
2. 规模变大后用 `python3 tools/wiki.py search "<关键词>"` 做 BM25 检索。
3. 读相关页，**带引用地**综合作答。引用格式：`（见 [[page-slug]]）`。
4. **好答案必须归档。** 如果回答包含对比、综合、新连接 —— 写入 `wiki/analyses/<slug>.md`，并回填索引与日志。
5. 若发现知识缺口，在回答末尾列出「建议补充的素材 / 建议深挖的问题」。

### 4.1 「库里没有 X」是有检索记录的断言

**说「库里没有 X」之前，必须先在库内检索一遍 —— 而且检索了哪些段落必须说清。**

「库里没有」是**很强的断言**，比「我找到了」更容易说错，因为**没有任何东西会提醒你漏了什么**。本库曾在一天之内因此错了三次，成因相同 —— 只检索了混层素材的摘要段与讲稿段，漏掉成书正文。

- 说「某素材没有 X」时，必须写明**检索了哪几段**（按分层表的段号 / 行区间）。只说「检索过」不成立。
- 素材是**混层的**，段与段的性质不同。在**一段**里没找到，不等于在**素材**里没有。
- 引用行号前**回原文核对一次**，不要凭记忆沿用。

> [!warning] 这不是「谨慎」的问题，是「断言强度」的问题
> 「**不可追溯**」与「**不存在**」是两种强度的断言（§3.6）。「库里没有」属于后者。
> 反过来：若检索后确实没有，**不要为了显得完整而含糊其辞**，直接写「没有」并注明检索范围。

## 5. 体检

人类说「检查一下知识库」时执行。跑 `python3 tools/wiki.py lint` 拿机器可查的部分，再人工补下面这些语义问题：

- **矛盾**：两页对同一事实给出不同说法 → 用 `> [!warning] 矛盾` 块标出，并列双方证据。
- **过期**：新素材已推翻旧结论 → 旧页标 `status: stale`，并链接到新页。
- **孤岛**：无入链的页面。
- **该建未建**：被反复提及但没有独立页的概念。
- **数据缺口**：可以靠一次网络搜索补上的空白。
- **建议**：下一批值得找的素材、值得问的问题。

**项目层** —— 机器可查的部分工具链已覆盖，语义部分靠人：

| 检查项 | 谁查 |
|---|---|
| 项目页缺 `goal`、`stage` 取值非法、未链接任何知识页 | 工具链报错 |
| **已 `shipped` 但「当前缺口」表未清空**（假 shipped） | 工具链报错 |
| 「当前缺口」表已清空但项目还开着 | 工具链提示 |
| 未被任何项目引用的知识页 | 工具链提示，逐个人工判断 |
| 长期无产出的项目（「产出」为空且 `stage: active`） | 人工：降级，或承认它是收藏而非项目 |
| 缺口过期的项目（条目是否还成立、已解决的有没有划掉） | 人工 |
| 没做优先级排序的项目（一条【阻塞】都没标） | 人工：逐条问「这一条真的不挡 `goal` 吗」 |

**机器可查的语义提示** —— `lint` 会打印，但**不计入问题数**：

| 提示 | 该怎么读 |
|---|---|
| **正文链接密度 < 1.5 条/千字** | 长文却几乎不在正文里引用别的页 = **清单式挂靠**（只写进 `related` 字段） |
| **名义交叉，实质同源** | `evidence_tier: crossed` 在这里不成立 |
| **未被任何项目引用的知识页** | 要么挂进某个项目，要么考虑是否还值得维护 |

**密度阈值 1.5 是实测标定的**：素材页密度中位数曾从 1.68 掉到 1.08（低于 1.5 的占比 40% → 83%），1.5 落在两批之间 —— 它是「能区分已知退化批次」的经验值，**不要随手调**。

> [!warning] 链接总数查不出这种退化
> `related` 字段与正文内链在 `lint` 口径里是**合并计数**的。一页哪怕正文里一句没提别的页，只要 `related` 写满，链接总数照样涨。
> 所以「页面数 / 链接数」这对数字**只衡量库有多大，不衡量知识有多结实**。要看结实程度，盯 **`single` 页占比**与**同源 crossed 数**。

每次 lint 完写一条日志：`python3 tools/wiki.py log lint "本轮发现 N 个问题"`。

## 6. 命名与写作

- 文件名：全小写，单词用 `-` 连接，英文 slug（`rag-vs-wiki`）。标题用中文写在 `title` 字段里。
- 素材文件名：`YYYY-MM-DD-slug.md`，日期是**收录日**。
- **重新抓取同一素材**时，新文件加 `-r2` / `-r3` 后缀，**不修改旧文件**。新文件 frontmatter 用 `supersedes` 指向旧版，`capture_note` 说明差异，并记入对应 `sources/` 页。
- 语气：直接、信息密度高。不要「值得注意的是」「综上所述」这类填充词。
- 数字与事实必须能追溯到 `sources`。**没有来源的断言要显式标注**：`（未验证）`。
- **`sources` 字段必须指向真正包含该内容的素材** —— 不允许悬空引用。
- **二手来源与一手来源冲突时，以一手为准，并记录纠正过程。**
- **综合页（`analyses/`）必须逐节点标注证据性质** —— 节点之间是「事实」还是「本库的推断」要分开说。
- **单来源的实体页要显式声明** —— 页尾用 `> [!note]` 说明，并降 `confidence`。这个字段已自动是 `single`；**机器只标「有几份来源」，标不了「这几份来源是什么性质」** —— 后半句仍须人工写。

### 6.1 防臃肿硬约束（2026-09-21 新增）

> **一句话判据：页面里只能有知识，不能有「我怎么得到这个知识的」。**
> 过程、记账、裁决、知识 —— 四层混在一页里，就是本库此前臃肿的根因。

写作时逐条自查；`lint` 会核其中可计算的部分。

| # | 约束 | 判据 |
|---|---|---|
| 1 | **单页长度上限** | concept / entity ≤ 200 行；source ≤ 260 行；analysis ≤ 300 行。超了就拆页，**不许靠写密来塞** |
| 2 | **要点节不得复述正文** | `## 关键要点` 是**导航**，3–8 条，每条一行。下面已有专门章节展开的内容，**要点里只给结论，不重复论证与引文** |
| 3 | **行号只留在引文处** | 叙述句里不标行号。知识页的引文坐标交给 `sources/` 页 —— 要核去那里 |
| 4 | **不写记账性语言** | 禁止「已登记」「不降级」「不计入 AI 占比」「按本库既有约定」「本库判断」这类**审核腔**。要表达判断就直接写判断，不要写「本库判断：X」（写成 X） |
| 5 | **不写过程流水** | 章节名里不许出现日期与批次（「2026-09-20 回填（模块八清单）」是流水，不是章节）。过程记 `log.md`，结论进页面 |
| 6 | **不重复自己** | 同一件事在本页只说一次；与别的页面的关系只写在 `## 与其他页面的关系` 一节 |
| 7 | **警示标记要克制** | ⚠️ 只留给真正的风险（不可追溯 / 伦理问题）。提醒性内容用普通行文 |
| 8 | **不用样板块** | 凡是 `lint` / 脚本能算出来的（`evidence_tier`、断链、标签），**不在正文里再写一遍** |

**核法**：`python3 tools/wiki.py lint` 报「页面超过长度上限」「章节名含日期 / 批次」「残留审核腔」「样板警示块」。

## 7. 工具链

```bash
python3 tools/wiki.py <command>

  init [path]              在当前/指定目录初始化一个新的知识库
  lint                     健康检查：断链、孤岛、缺 frontmatter、重复 slug、项目层、证据层级、**防臃肿**
  stats                    统计：各类型页面数、链接数、孤立页、项目阶段分布、证据层级分布
  search "<query>"         BM25 全文检索（支持中文二字组）
  index                    从各页 frontmatter 重建 wiki/index.md
  build                    生成单文件浏览站点 site/index.html
                           （同时写 site/.build-manifest.json —— 判据 3 的基准）
  buildcheck               对比构建基准，报「新建 / 更新 / 已删除」页数并给判定
  chapter-audit [-v]       source 页正文区 / 账目区对账
  template-check           核 templates/*.md 与 wiki.py 内联兜底模板是否一致
  log <type> "<message>"   追加一条日志
  new <type> <slug>        按模板新建页面（project / source / entity / concept / analysis）
  graph                    打印链接关系（便于发现枢纽页与孤岛）
```

**零依赖**：只用 Python 标准库，不需要 pip install。

> [!note] 「页面总数」有两个口径
> `lint` / `build` **含** meta 页，`index` **不含**。判断 index 是否过期要**比 `wiki/` 文件数与 index 条目数**，不要比这两个数。

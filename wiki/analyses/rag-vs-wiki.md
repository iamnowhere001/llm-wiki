# RAG 与 LLM Wiki 的对比

> 结论：两者不是「好检索」与「差检索」的关系，而是**知识在哪里被编译**的关系。RAG 在查询时编译（每次都重算），LLM Wiki 在收录时编译（编译一次、持续保鲜）。选择取决于素材的复用频率与稳定程度。

- **触发问题**：既然 RAG 已经能基于文档回答问题，为什么还要额外维护一层 wiki？
- **结论**：当同一批素材会被反复提问、且问题需要跨文档综合时，LLM Wiki 的成本结构更优；一次性问答用 RAG 更划算。

## 对比

| 维度 | RAG | LLM Wiki |
|---|---|---|
| 知识编译时机 | 查询时，每次都重算 | 收录时，一次编译 |
| 是否累积 | 否 | 是（见 [[compounding-knowledge]]） |
| 跨文档综合 | 每次重新拼装碎片 | 综述已存在于页面上 |
| 矛盾处理 | 每次可能给出不同结论 | 收录时标注，稳定可查 |
| 交叉引用 | 无（检索时临时发现） | 预先建好，可浏览 |
| 提问的产物 | 留在聊天记录里 | 可归档回 wiki（`analyses/`） |
| 维护成本 | 近零 | 高 —— 但由 LLM 承担 |
| 基础设施 | 需要嵌入索引、向量库 | 中等规模下只需 `index.md`（见 [[index-and-log]]） |
| 规模上限 | 高 | 数千页后需要检索工具（见 [[qmd]]） |
| 可解释性 | 依赖检索到的块 | 每页可单独审阅、可 diff |

## 证据

1. 作者对 RAG 的描述：「LLM 每次都在从零重新发现知识。要综合五份文档才能回答的问题，每次都得重新拼装。」（见 [[2026-09-18-karpathy-llm-wiki]]）
2. 作者点名的 RAG 实例：[[notebooklm]]、ChatGPT 文件上传、大多数 RAG 系统。
3. 关于规模：作者明确说索引方案在 ~100 份素材、数百页规模下「效果出奇地好」，且**避免了嵌入检索基础设施**。
4. 关于维护成本：作者认为人类放弃 wiki 是因为维护成本增长快于价值增长，而 LLM「不会厌烦、不会忘记更新引用、能一次改 15 个文件」。

## 结论与适用条件

**选 LLM Wiki**：
- 素材会被反复提问，且问题需要跨素材综合
- 素材相对稳定（论文、书籍、长文、会议纪要）
- 你希望知识**随时间变得更结构化**，而不只是「能查到」

**选 RAG**：
- 一次性问答，或素材只被问一次
- 素材高度易变（新闻、股价），编译产物会立刻过期
- 需要精确回溯原文片段（wiki 是压缩后的二次产物）
- 规模极大，且不需要综合（纯查找）

**可以共存**：wiki 负责综合与长期结构，RAG 负责在 `raw/` 里做精确原文检索。本仓库的 `tools/wiki.py search` 目前只覆盖 wiki 层。

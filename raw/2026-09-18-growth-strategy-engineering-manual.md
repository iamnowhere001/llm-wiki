# 一、系统架构 (System Architecture)

## 1.1 设计原则

在设计架构之前，需要明确三个原则：

1. **最小化意志力依赖**: 好的系统不应该要求用户"自律"，而是通过机制自动运行
2. **可测量优先**: 无法测量的改进是盲目的
3. **容错是第一天性**: 系统必然崩溃，区别在于能否快速恢复

**每层职责**:

- **感知层**: 接收内外部信号，判断"系统状态"
- **动机层**: 基于感知结果，产生行动倾向
- **决策层**: 在多个可能行动中选择
- **执行层**: 将决策转化为具体行动
- **反馈层**: 评估行动结果，更新系统状态
- **进化层**: 基于长期数据，升级系统本身

# 二、协议设计 (Protocol Design)

每个工具都被设计为一个独立的**协议(Protocol)**，具有明确的输入、输出、触发条件和执行流程。

## 2.1 感知层协议

### 2.1.1 自由能对齐协议 (FreeEnergyAlignment Protocol)

**触发条件**:

- 每日晨间启动
- 遇到意外事件
- 决策前检查

**输入**:

- 当前预测（"我认为会发生X"）
- 实际发生（"X确实发生了"或"Y发生了"）

**执行流程**:

```Plaintext
Step 1: 误差检测
  IF 实际 == 预测:
      surprise_level = 0 (无惊讶)
      输出: "预期确认，继续当前轨道"
  ELSE:
      surprise_level = |实际 - 预测| / 预测范围
      输出: "预测误差 = surprise_level"

Step 2: 惊讶度分级
  IF surprise_level < 0.1:
      输出: "微小惊讶 → 小幅更新认知"
      执行: 增量学习
  ELIF surprise_level < 0.5:
      输出: "适度惊讶 → 重新评估框架"
      执行: 调用视角协议
  ELIF surprise_level < 0.8:
      输出: "重大惊讶 → 系统性重构"
      执行: 认知解耦协议
  ELSE:
      输出: "冲击性惊讶 → 触发断路器"
      执行: 强制安全模式

Step 3: 学习更新
  更新预测模型
  记录: 预测 ← 实际
  调整未来预测权重
```

**输出**:

- surprise_level: float (0-1)
- action_taken: str
- updated_prediction_model: dict

**失败模式**:

- **过度否认**: 忽略意外，强行维持旧预测 → 缓解: 设置"否认检测"，连续3次偏差>30%强制触发Step 2
- **过度反应**: 把所有意外当作重大信号 → 缓解: 设置阈值，低于阈值的意外只记录不行动

**与其他协议接口**:

- surprise_level > 0.5 → 触发认知解耦协议
- surprise_level > 0.8 → 触发安全协议

### 2.1.2 场域感知协议 (FieldPerception Protocol)

**触发条件**:

- 进入新环境（新公司、新城市、新团队）
- 遇到规则模糊的情境
- 重要决策前

**输入**:

- 当前场域标识（"这是一个什么场域？"）
- 观察到的行为模式

**执行流程**:

```Plaintext
Step 1: 场域识别
  询问: "这个场域奖励什么？"
  询问: "这里的'好'是什么定义？"
  询问: "谁有裁判权？"
  
  输出: 
    field_type: enum(商业/学术/官僚/创意/社交/家庭)
    reward_definition: str
    authority_structure: str
    capital_exchange_rate: dict

Step 2: Doxa检测（场域的默认信念）
  观察: 这里的人认为什么是"理所当然"的？
  观察: 什么行为会被自然地认可/否定？
  观察: 有哪些"不能说的规则"？
  
  输出: 
    doxa_beliefs: list[str]
    forbidden_actions: list[str]

Step 3: 惯习兼容性检查
  询问: "我的默认行为模式与场域兼容吗？"
  询问: "我需要调整哪些行为？"
  
  IF 兼容度 < 50%:
      输出: "高摩擦 → 考虑换场域或深度调整"
  ELIF 兼容度 < 80%:
      输出: "中等摩擦 → 保持核心，调整表层"
  ELSE:
      输出: "高兼容 → 可以专注执行"

Step 4: 资本识别
  识别: 在这个场域，什么是有效资本？
  识别: 我现在拥有哪些资本？
  识别: 资本之间的汇率是什么？
  
  输出:
    effective_capitals: list[enum(经济/社会/文化/符号)]
    my_capitals: dict
    conversion_rates: dict
```

**输出**:

- field_analysis: dict
- recommended_approach: str
- capital_position: dict

**失败模式**:

- **场域误判**: 用错误框架解读情境 → 缓解: 设置"第二意见"机制，请教熟悉该场域的人
- **过度适应**: 为了适应场域放弃核心价值 → 缓解: 身份守护进程介入，检测"一致性"

### 2.1.3 认知解耦协议 (CognitiveDecoupling Protocol)

**触发条件**:

- 自由能协议检测到重大惊讶
- 自我报告: 负面情绪强度 > 7/10
- 他人反馈: "你好像陷进去了"

**输入**:

- 当前情绪状态
- 触发情绪的事件描述

**执行流程**:

```Plaintext
Step 1: 认知解离 (Defusion)
  目标: 从"我"中分离出"想法"
  
  操作:
    - 给想法命名: "我正在经历一个'我被拒绝'的想法"
    - 观察想法而非认同想法: "这个想法在我脑中飘过"
    - 标注想法类型: "这是一个'灾难化'类型想法"
  
  输出: thought_separated = True

Step 2: 视角调用 (Perspective Taking)
  目标: 从第三方视角观察情境
  
  操作:
    - "如果是我最好的朋友遇到这件事，我会怎么说？"
    - "十年后再看这件事，它还重要吗？"
    - "这件事的最坏结果真的会发生吗？有多大可能？"
  
  输出: perspective_shifted = True

Step 3: 认知重评 (Reappraisal)
  目标: 重新解读事件的意义
  
  操作:
    - "这个挫折中隐藏着什么机会？"
    - "对方的意图真的像我以为的那样吗？"
    - "如果这是为我好，它怎么可能是为我好？"
  
  输出: 
    reframed_meaning: str
    emotion_intensity_after: int

Step 4: 行动决策
  IF emotion_intensity_after < 4/10:
      输出: "可以正常行动"
  ELSE:
      输出: "需要更多时间或支持"
      触发: 安全协议或社交支持请求
```

**输出**:

- thought_separated: bool
- perspective_shifted: bool
- reframed_meaning: str
- emotion_intensity_before/after: int
- recommended_action: str

**失败模式**:

- **跳过解离直接重评**: 用新解释掩盖情绪 → 缓解: 必须按顺序执行，验证每个步骤
- **理性化过度**: "我理解了这不重要"但情绪未处理 → 缓解: 验证emotion_intensity_after是否真实下降

## 2.2 动机层协议

### 2.2.1 自我决定驱动协议 (SDT-Driven Protocol)

**触发条件**:

- 每日早晨（动机状态检查）
- 任务执行前
- 动机不足自我报告

**输入**:

- 当前任务描述
- 当前自主感/胜任感/关系感水平

**执行流程**:

```Plaintext
Step 1: 需求诊断
  评估:
    autonomy_level: 当前行动是我的选择吗？我能调整吗？
    competence_level: 这个任务我能做好吗？有成长空间吗？
    relatedness_level: 我做这件事与他人有连接吗？
  
  输出:
    dominant_need: enum(自主/胜任/关系)
    satisfaction_gaps: dict

Step 2: 动机质量检测
  询问: "我为什么做这件事？"
  
  选项:
    A. 因为别人让我做 → 外部调节
    B. 因为不做会内疚 → 内摄调节
    C. 因为这很重要 → 认同调节
    D. 因为这就是我的一部分 → 内在动机
  
  IF 动机质量 < C:
      输出: "低质量动机 → 需要重新框架"
      转向: "我如何把这个任务与我的价值连接？"

Step 3: 需求补足
  IF autonomy_gap > 0:
      操作:
        - "这件事中，有哪些部分是我可以选择的？"
        - "有没有我忽略的自主空间？"
        - "如果必须做，我选择什么时候/如何做？"
  
  IF competence_gap > 0:
      操作:
        - "我能从这个小成功开始吗？"
        - "谁可以给我反馈帮助我成长？"
        - "成长空间在哪里？"
  
  IF relatedness_gap > 0:
      操作:
        - "做这件事能与谁产生连接？"
        - "我能与谁分享进展？"
        - "我能为谁做这件事？"

Step 4: 行动确认
  确认: 新框架下，我愿意做这件事吗？
  IF YES: 执行任务
  IF NO: 
      - 重新评估任务必要性
      - 考虑委托/拒绝/延后
```

**输出**:

- motivation_quality: enum(外部/内摄/认同/内在)
- need_satisfaction_plan: dict
- action_readiness: bool

**失败模式**:

- **伪自主**: "我选择这样做"但实际上是因为怕惩罚 → 缓解: 深度追问"如果没人知道，我会做吗？"
- **胜任感幻觉**: 任务太简单导致无聊 → 缓解: 检测"无聊信号"，自动提高任务挑战

### 2.2.2 安全感维护协议 (SecurityMaintenance Protocol)

**触发条件**:

- 系统启动时
- 压力事件后
- 每周安全基线检查

**输入**:

- 当前安全指标（身体/情感/财务/关系）

**执行流程**:

```Plaintext
Step 1: 安全基线检测
  评估四个维度（每项0-25，满分100）:
    physical_safety: 我有足够的健康保障吗？我感到身体安全吗？
    emotional_safety: 我有一个可以信任的人吗？我能表达脆弱吗？
    financial_safety: 我有基本的经济保障吗？三个月不工作能活吗？
    existential_safety: 我有身份认同吗？我有意义感吗？
  
  输出:
    total_safety_score: int (0-100)
    weak_dimensions: list

Step 2: 安全模式判定
  IF total_safety_score < 40:
      状态 = "安全模式"
      输出: "系统优先修复安全感，非必要事务暂停"
  ELIF any_dimension < 15:
      状态 = "警戒模式"
      输出: "某维度需要紧急关注"
  ELSE:
      状态 = "正常运行"

Step 3: 安全基地 vs 安全港湾
  检查: 当前是"探索状态"还是"休整状态"？
  
  IF 探索状态（场域感知协议识别为需要外出探索）:
      需求 = 安全基地（出发前的基础保障）
      操作:
        - 我的后方的确有人/系统支撑我吗？
        - 最坏情况有兜底吗？
  
  IF 休整状态（刚从高压环境回来）:
      需求 = 安全港湾（可以卸下防备的回归地）
      操作:
        - 我现在在安全的地方吗？
        - 我可以允许自己脆弱吗？

Step 4: 安全投资决策
  识别最薄弱维度
  决策: 
    - 短期: 是否需要立即行动补足？
    - 中期: 安全建设计划是什么？
    - 长期: 如何建立可持续的安全基础？
```

**输出**:

- safety_score: int
- safety_mode: enum(正常/警戒/安全模式)
- recommended_actions: list

**失败模式**:

- **安全忽视**: 过度追求成长而忽视基础安全 → 缓解: 安全分数低于阈值时强制锁定非必要行动
- **安全成瘾**: 过度准备而不敢行动 → 缓解: 设置"最小安全标准"，达到即行动

### 2.2.3 复利积累协议 (CompoundInterest Protocol)

**触发条件**:

- 每周资本审查
- 每月复盘
- 季度战略审视

**输入**:

- 七种资本的当前状态
- 时间投入记录
- 回报数据

**执行流程**:

```Plaintext
Step 1: 资本盘点
  评估七种资本（每种0-10分）:
    financial_capital: 金钱、投资、资产
    human_capital: 技能、知识、能力
    health_capital: 身体、精神、活力
    social_capital: 关系、网络、信任
    reputation_capital: 声望、信誉、品牌
    psychological_capital: 心态、韧性、情绪
    experiential_capital: 经历、体验、记忆
  
  输出: capital_sheet: dict

Step 2: 复利潜力评估
  询问每个资本:
    - 这个资本可以"利息再生利息"吗？
    - 积累时间越长，这个资本的价值增长越快吗？
    - 我是处于"积累侧"还是"消耗侧"？
  
  输出:
    compound_candidates: list[capital_names]
    consume_only: list[capital_names]

Step 3: 时间杠杆分析
  核心问题: "早开始一年，收益增加多少？"
  
  计算:
    对于每个compound_candidate:
      year_25_value = f(years=35)  # 假设25岁开始
      year_35_value = f(years=25)  # 假设35岁开始
      time_premium = year_25_value / year_35_value
  
  输出: 
    priority_capitals: 按时间杠杆排序

Step 4: 行动决策
  决策:
    - 每月投入多少时间/金钱到每个资本？
    - 如何平衡"消耗型"和"积累型"活动？
    - 哪些资本的"利息"可以再投资？
  
  输出:
    monthly_investment_plan: dict
    compound_acceleration: float (预期复利增速)
```

**输出**:

- capital_sheet: dict
- priority_capitals: list
- monthly_investment_plan: dict
- compound_rate: float

**失败模式**:

- **虚假复利**: 把消耗当积累（如无效社交、伪学习） → 缓解: 验证"利息是否真实产生"
- **短期主义**: 为短期回报牺牲长期积累 → 缓解: 设置"年度最低积累额"

### 2.3.1 能耐寻求协议 (CapabilitySeeking Protocol)

**输入**:

- 当前目标/问题

```Plaintext
Step 1: 奴隶检测
  询问:
    - "我目前最追求的是什么目标？"
    - "我愿意为这个目标牺牲其他所有吗？"
    - "如果我失败了，我的人生就没有意义了吗？"
  
  IF 是 → 标记: "单目标优化警告"
     询问: "这个目标服务于什么更高目标？"
     询问: "有没有其他方式实现这个更高目标？"

Step 2: 选项生成
  核心原则: 永远要有"第三个选项"
  
  框架:
    - 选项A: 默认选项（维持现状）
    - 选项B: 明显选项（通常的替代方案）

    - "有没有可能同时做到A和B的某个C？"

Step 3: 赋能评估

    - "这个选项增加还是减少了未来的选择？"
    - "这个选项是让我成为工具还是主人？"
    - "这个选项在多久的时间范围内有效？"
  
  输出:
    empowerment_scores: dict
    best_for_agency: option_name

Step 4: 决策
  IF best_for_agency 得分显著高于其他:
      建议: 选择能耐寻求最优解
  ELSE:
      建议: 使用多目标决策框架
```

**输出**:

- slavery_indicators: list
- options_generated: list
- empowerment_scores: dict
- recommended_option: str
- reasoning: str

**失败模式**:

- **虚假选项**: 生成的都是同一框架下的变体 → 缓解: 必须明确生成"打破框架"的C选项
- **分析瘫痪**: 选项太多无法决策 → 缓解: 设置"决策截止时间"，超时强制简化

### 2.3.3 探索-利用平衡协议 (ExploreExploit Protocol)

**触发条件**:

- 每月探索预算审查
- 遇到新机会时
- 感觉进入舒适区时

**输入**:

- 当前年龄/预期剩余时间
- 当前利用项目的收益曲线
- 可用探索资源

**执行流程**:

```Plaintext
Step 1: 剩余时间评估
  问题:
    - 我的预期寿命是多少？（用于计算剩余时间）
    - 我的预期活跃期（还想做大事的时间）多长？
  
  使用吉廷斯指数框架:
    剩余时间越长 → 探索价值越高
    剩余时间越短 → 利用价值越高

Step 2: 利用收益评估
  评估当前"利用"项目:
    - 边际收益是在上升还是下降？
    - 是否有触顶信号？
    - 继续投入的边际回报是多少？
  
  输出:
    exploit_returns: enum(上升/平稳/下降)
    marginal_return_rate: float

Step 3: 探索预算计算
  基础公式:
    exploration_budget = base(年龄) × 总资源 × 剩余时间权重
  
  调整因素:
    - exploit_returns下降 → 提高探索预算
    - 新场域机会 → 提高探索预算
    - 连续利用成功 → 适度降低探索（但保持底线）

Step 4: 探索-利用决策
  IF exploit_returns 正在下降 AND 探索预算充足:
      建议: 提高探索比例
  ELIF exploit_returns 稳定/上升:
      建议: 维持或适度降低探索
  ELIF 重大新机会出现:
      建议: 即使压缩利用也要抓住

实际分配示例（基于年龄）:
  - 25岁: 70%探索，30%利用
  - 35岁: 50%探索，50%利用
  - 45岁: 30%探索，70%利用
  - 55岁+: 10-20%探索，80-90%利用
```

**输出**:

- gittins_index: float
- exploration_budget: dict
- recommended_ratio: str
- specific_explore_actions: list

**失败模式**:

- **探索陷阱**: 永远在探索不利用 → 缓解: 设置"利用承诺"，探索到某个阶段必须承诺利用
- **利用陷阱**: 拒绝探索直到边际收益归零 → 缓解: 提前设置"探索触发器"，收益下降X%自动提高探索

### 2.3.4 WOOP执行协议 (WOOP Protocol)

**触发条件**:

- 目标确认后
- 习惯养成启动
- 障碍预防

**输入**:

- Wish: 愿望
- Outcome: 期望结果
- Obstacle: 预期障碍
- Plan: 执行计划

**执行流程**:

```Plaintext
Step 1: Wish确认（工程化版）
  要求: 具体、可衡量、有期限
  格式: "在[时间]前实现[具体指标]"
  验证: "这是'我要'还是'要我'？"

Step 2: Outcome定义（工程化版）
  要求: 必须是可观测、可验证的
  格式: "当[可观测证据]出现，则成功"
  示例: "体重<75kg"比"变得更健康"更好

Step 3: Obstacle分析（工程化版）
  不是"可能的障碍"，而是"最可能的阻碍"
  
  分类:
    - 内部障碍: 习惯、情绪、能力
    - 外部障碍: 环境、资源、时机
  
  优先级:
    - 识别最大的1-2个障碍
    - 不是所有障碍都要解决
    
  关键问题:
    "这个障碍的本质是什么？"
    "它是'真的做不到'还是'做起来不舒服'？"

Step 4: If-Then编程（核心）
  格式: "IF [障碍出现] THEN [自动行动]"
  
  示例:
    IF 晚上10点想吃零食 THEN 喝一杯水+刷牙
    IF 想要刷手机 THEN 先做3个深呼吸
    IF 想要拖延 THEN 先做5分钟再说
  
  原则:
    - 动作要小且具体
    - 可以连续多个If-Then
    - 执行不需要意志力

Step 5: 实施与追踪
  每日检查:
    - If-Then被触发了多少次？
    - 触发时执行了吗？
    - 需要调整If-Then吗？
  
  每周复盘:
    - 障碍分析准确吗？
    - If-Then有效吗？
    - Wish需要调整吗？
```

**输出**:

- wish: str (具体化)
- outcome: str (可验证)
- main_obstacle: str
- if_then_chain: list[dict]
- execution_rate: float

**失败模式**:

- **If-Then过泛**: "IF有障碍 THEN克服它" → 无效，因为没有具体动作 → 缓解: If-Then必须小且具体
- **计划过度**: 写了20个If-Then → 无效，因为记不住 → 缓解: 最多3个核心If-Then

## 2.4 执行层协议

### 2.4.1 主动高认知负荷协议 (HighCognitiveLoad Protocol)

**触发条件**:

- 需要专注工作时
- 发现自己在逃避任务时
- 注意力分散时

**输入**:

- 当前任务
- 干扰清单

**执行流程**:

```Plaintext
Step 1: 任务吸引力诊断
  核心原则: 不是"减少干扰"，而是"增加任务吸引力"
  
  评估任务:
    - 这个任务有挑战吗？（难度 vs 能力）
    - 这个任务有即时反馈吗？
    - 这个任务有意义吗？
    - 这个任务我能掌控吗？
  
  输出:
    task_attractiveness: 0-10
    attractiveness_gaps: list

Step 2: 吸引力提升
  IF 任务太简单:
      操作:
        - 增加难度
        - 给自己设更高目标
        - 加入创意限制
  
  IF 缺乏即时反馈:
      操作:
        - 设置小里程碑
        - 给自己打分
        - 想象完成后奖励
  
  IF 缺乏意义:
      操作:
        - 连接更高目的
        - 想象对他人影响
        - 重新定义任务价值
  
  IF 缺乏掌控:
      操作:
        - 分解任务增加选择
        - 决定执行顺序
        - 设置自己的规则

Step 3: 干扰重新框架
  不是"排除干扰"，而是"干扰vs任务，哪边更有趣？"
  
  问题:
    - "现在刷手机比这个任务更有趣吗？"
    - "如果这个任务足够吸引我，干扰还会存在吗？"
  
  IF 任务更有趣: 无需意志力，自动专注
  IF 干扰更有趣: 需要提升任务吸引力，或暂时隔离干扰

Step 4: 执行设置
  - 关闭通知
  - 物理隔离干扰源
  - 设定专注时段
  - 准备好所需资源（避免"等等"）
```

**输出**:

- task_attractiveness_score: int
- attractiveness_boosts: list
- execution_readiness: bool

**失败模式**:

- **伪吸引力**: 用"应该有趣"欺骗自己 → 缓解: 诚实评估，如果真的无趣，考虑放弃或重构
- **过度依赖意志力**: 把"减少干扰"当主要手段 → 缓解: 回到Step 1，提升任务吸引力

### 2.4.2 供给侧心态协议 (SupplySideMindset Protocol)

```Plaintext
Step 1: 心态检查

    - 视角: 我能看到什么别人看不到的？
  
  输出: supply_catalog: list

Step 3: 接口开放

Step 5: 拒绝零和触发器

    - 自问: "这是真的零和吗？"
    - 自问: "有没有正和的可能？"
    - 寻找"做大蛋糕"的方案
```

**输出**:

- current_mindset: enum(供给者/需求者)
- supply_catalog: list
- open_interfaces: list
- pending_collaborations: list

**失败模式**:

- **虚假供给**: 提供别人不需要的价值 → 缓解: 先了解对方真正需要什么
- **供给过剩**: 无差别供给导致精力耗散 → 缓解: 选择性供给，优先高价值匹配

### 2.4.3 社交资本行动协议 (SocialCapitalAction Protocol)

**触发条件**:

- 需要扩展网络时
- 进入新环境时
- 重要目标需要资源时

**输入**:

- 当前目标
- 现有关系网络
- 目标所需资源

**执行流程**:

```Plaintext
Step 1: 关系网络盘点
  评估现有网络:
    - 强联系: 家人、密友（高信任、低信息多样性）
    - 弱联系: 点头之交、社交场合认识的人（低信任、高信息多样性）
  
  关键认知: 弱联系往往带来新机会

Step 2: 结构洞识别
  识别:
    - 我的网络中哪些群体之间没有连接？
    - 我是否处于不同群体的"桥梁"位置？
    - 我需要连接哪两个群体？
  
  价值: 处于结构洞 = 拥有信息优势

Step 3: 弱联系维护策略
  核心: 定期接触，不让关系断掉
  
  方法:
    - 每季度联系一次（不是有求于人才联系）
    - 提供价值先于索取
    - 关注对方动态，适时回应
  
  量化: 
    - 维护10个弱联系 ≈ 每月2-3次接触
    - 记录在关系管理系统中

Step 4: 搬家决策
  问题: "我需要物理位移到机会多的地方吗？"
  
  考量因素:
    - 当前场域的机会密度
    - 目标场域的网络效应
    - 搬家的成本与收益
  
  决策树:
    - 机会密度高的场域有可触及的网络吗？
    - 如果没有，考虑地理迁移

Step 5: 关系资本投资
  分配社交时间:
    - X% 维护强联系（深度交流）
    - Y% 维护弱联系（保持连接）
    - Z% 探索新关系（扩展网络）
  
  建议配比（根据目标）:
    - 机会探索期: 20%强/30%弱/50%新
    - 执行深耕期: 40%强/40%弱/20%新
    - 稳定维持期: 50%强/40%弱/10%新
```

**输出**:

- network_map: dict
- structural_holes: list
- bridge_opportunities: list
- relationship_investment_plan: dict

**失败模式**:

- **关系空转**: 认识很多人但无深度连接 → 缓解: 定期评估"谁能在我需要时真正帮忙"
- **过度社交**: 把所有时间用于社交 → 缓解: 设置社交时间上限

## 2.5 反馈层协议

### 2.5.1 共鸣事件记录协议 (ResonanceEvent Protocol)

**触发条件**:

- 被某事物深深触动时
- 感到"世界有回响"时
- 体验到深度连接时

**输入**:

- 当前体验描述
- 共鸣类型

**执行流程**:

```Plaintext
Step 1: 共鸣识别
  判断: 这是否是一次共鸣事件？
  
  共鸣特征:
    - 你不再只是"使用"某物，而是感到它在"回应"你
    - 有一种"被接通"的感觉
    - 不是控制感，而是共振感
    - 事后的充实感而非空虚感
  
  区分:
    - 共鸣 ≠ 点赞（单向vs双向）
    - 共鸣 ≠ 占有（使用vs连接）
    - 共鸣 ≠ 享乐适应（持久满足vs短暂快感）

Step 2: 共鸣类型分类
  横向共鸣（人与人）:
    - 对话中产生第三种想法
    - 被深深理解
    - 合作中涌现创造力
  
  斜向共鸣（人与物/工作）:
    - 创作时感到材料在"配合"
    - 工作成果有"生命"
    - 技能精进带来快感
  
  纵向共鸣（人与宏大存在）:
    - 站在壮丽风景前感到敬畏
    - 理解深刻真理时的顿悟
    - 使命感召唤

Step 3: 共鸣事件记录
  记录格式:
    - 时间:
    - 类型:
    - 触发物:
    - 体验描述:
    - 收获/感悟:
    - 后续行动:

Step 4: 共鸣资产盘点
  每周:
    - 记录了多少次共鸣事件？
    - 哪些类型最多？
    - 是否有"共鸣饥饿"信号？（只做事没有共鸣）
  
  每月:
    - 共鸣事件趋势如何？
    - 需要增加哪些共鸣来源？
    - 是否有异化信号？

Step 5: 共鸣行动计划
  基于盘点结果:
    - 增加共鸣来源？
    - 减少异化活动？
    - 创造更多共鸣机会？
```

**输出**:

- resonance_events: list
- resonance_score: float
- alienation_signals: list
- resonance_plan: dict

**失败模式**:

- **共鸣上瘾**: 追求共鸣而逃避必要工作 → 缓解: 区分"共鸣滋养"和"共鸣逃避"
- **共鸣虚假**: 把刺激当共鸣 → 缓解: 检查事后充实感，而非当时快感

## 2.6 身份相关协议

### 2.6.1 身份守护协议 (IdentityGuardian Protocol)

**触发条件**:

- 重大决策前
- 身份受到挑战时
- 日常行动一致性检查

**输入**:

- 自我定义的身份
- 当前行动/选择

**执行流程**:

```Plaintext
Step 1: 身份定义检查
  问题: "我是谁？"
  
  不是问职业/角色，而是问:
    - "我坚持什么价值？"
    - "我拒绝什么？"
    - "我为什么存在？"
  
  输出: identity_statement: str
  示例: "我是一个用理性探索真相的人"

Step 2: 皮肤vs衣服检测
  问题: "我现在是把身份当皮肤还是当衣服？"
  
  皮肤特征（低阶）:
    - 身份被批评 = 我被批评
    - 必须维护身份
    - 无法接受身份变化
  
  衣服特征（高阶）:
    - 身份是工具，我可以穿脱
    - 身份服务于我，而非相反
    - 愿意更新身份
  
  IF skin_mode:
      输出: "皮肤模式 → 需要解耦"
      触发: 认知解耦协议

Step 3: 行动-身份一致性
  问题: "这个行动与我的身份一致吗？"
  
  一致性检查:
    - 这个选择是"我要做"还是"要我做"？
    - 如果没人知道，我还会这样做吗？
    - 这是身份的表达还是身份的妥协？

Step 4: 身份驱动 vs 外力驱动
  IF 外力驱动:
      追问:
        - "为什么我允许这个外力控制我？"
        - "我如何重新获得主动权？"
        - "这是我主动选择的服从，还是被动的顺从？"

Step 5: 身份进化
  问题: "我的身份需要更新吗？"
  
  信号:
    - 旧身份限制了成长
    - 新经历扩展了自我
    - 核心价值不变但表达方式变了
  
  操作:
    - 扩展身份而非替换
    - 保留核心，更新表层
```

**输出**:

- identity_statement: str
- current_mode: enum(皮肤/衣服)
- consistency_score: float
- action_recommendation: str

**失败模式**:

- **身份僵化**: 无法更新身份以适应成长 → 缓解: 定期"身份体检"
- **身份虚无论**: 没有任何身份 → 缓解: 至少需要一个临时身份作为行动锚点

# 三、仪表盘设计 (Dashboard Design)

## 3.1 设计原则

- **可量化**: 每个指标必须能转化为数字
- **可追踪**: 每周至少有一次数据更新
- **可操作**: 看到数据后知道该做什么

## 3.2 核心KPI设计

### 3.2.1 七大核心指标

| 指标 | 类型 | 目标值 | 说明 |
|-|-|-|-|
| 安全基线分 | 状态指标 | > 70 | 四维度综合安全感 |
| 动机质量指数 | 领先指标 | ≥ 内在动机 | SDT六层动机评估 |
| 选项丰富度 | 领先指标 | ≥ 3 | 能耐定理：备选方案数 |
| 认知负荷得分 | 过程指标 | 7-8/10 | 任务吸引力适中 |
| 复利积累率 | 滞后指标 | 正增长 | 七资本综合增长 |
| 共鸣密度 | 体验指标 | ≥ 3次/周 | 共鸣事件频率 |
| 身份一致性 | 过程指标 | > 80% | 身份驱动vs外力驱动 |

### 3.2.2 领先指标 vs 滞后指标

| 类型 | 指标 | 说明 | 预警作用 |
|-|-|-|-|
| **领先** | 动机质量 | 动机下降预示后续行动下降 | ⬆️ 提前1-2周预警 |
| **领先** | 选项丰富度 | 选项减少预示被困住 | ⬆️ 提前1个月预警 |
| **领先** | 安全基线 | 安全下降预示系统脆弱 | ⬆️ 实时监控 |
| **滞后** | 复利积累率 | 结果验证 | ⬇️ 确认长期效果 |
| **滞后** | 共鸣密度 | 体验质量验证 | ⬇️ 确认意义感 |
| **过程** | 认知负荷得分 | 当前状态 | ⚡ 实时调整 |

### 3.2.3 红黄绿阈值设计

```Plaintext
安全基线分 (0-100):
  🔴 < 40: 安全模式 - 暂停非必要行动，优先修复
  🟡 40-70: 警戒模式 - 关注但可继续
  🟢 > 70: 正常运行

动机质量指数 (1-6):
  🔴 1-2 (无动机/外部): 需要立即重新框架
  🟡 3 (内摄): 注意意志力消耗
  🟢 4-6 (认同/内在): 正常运作

选项丰富度 (整数):
  🔴 1: 被困住 - 强制执行能耐寻求协议
  🟡 2: 有限 - 增加选项生成
  🟢 ≥ 3: 丰富 - 正常决策

认知负荷得分 (0-10):
  🔴 < 4: 无聊 - 增加挑战
  🟡 4-6: 偏低 - 适度增加
  🟢 7-8: 最佳 - 维持
  🔴 > 8: 过高 - 分解任务

复利积累率 (季度变化):
  🔴 负增长: 消耗状态 - 审查支出
  🟡 零增长: 停滞 - 增加投资
  🟢 正增长: 积累 - 维持并优化

共鸣密度 (次/周):
  🔴 0: 异化信号 - 增加共鸣活动
  🟡 1-2: 偏低 - 关注趋势
  🟢 ≥ 3: 正常 - 多样化来源

身份一致性 (0-100%):
  🔴 < 50%: 严重偏离 - 重新审视决策
  🟡 50-80%: 部分偏离 - 注意调整
  🟢 > 80%: 一致 - 正常运作
```

# 五、容错与韧性设计 (Fault Tolerance Design)

## 5.1 设计原则

系统必然崩溃。容错设计的核心不是"防止崩溃"，而是"让崩溃可恢复"。

## 5.2 降级策略（安全模式）

### 5.2.1 三级运行模式

```Plaintext
flowchart TD
    A[🟢 正常运行] -->|安全基线≥70, 能量≥50%| B[全部协议执行]
    
    C[🟡 降级运行] -->|安全基线40-70, 或能量30-50%| D[仅核心协议]
    D --> D1[感知层、动机层]
    D --> D2[暂停探索协议]
    D --> D3[禁止重大决策]
    
    E[🔴 安全模式] -->|安全基线<40, 或能量<30%| F[仅安全协议]
    F --> F1[安全基线修复]
    F --> F2[基本生存活动]
    F --> F3[禁止:新项目、新决策]
    
    B -.->|条件恶化| C
    C -.->|条件恶化| E
    E -.->|恢复条件| C
    C -.->|恢复正常| B
```

### 5.2.2 能量管理规则

```Plaintext
能量等级与操作权限:

🔴 极低能量 (0-20%):
  - 只执行"必须做"的事项
  - 禁止: 新任务、社交、决策
  - 行动: 休息、恢复、必要医疗

🟡 低能量 (20-40%):
  - 只执行"应该做"的高优先级事项
  - 允许: 简单的例行任务
  - 禁止: 创造性工作、复杂社交
  - 行动: 减少消耗，增加小恢复

🟢 中能量 (40-70%):
  - 可以执行"想要做"的事项
  - 允许: 日常工作、学习
  - 建议: 减少消耗，适当积累

🟢 高能量 (70-100%):
  - 可以执行任何事项
  - 建议: 追求成长目标、探索新领域、承担适度风险
```

## 5.3 断路器设计

### 5.3.1 断路器清单

| 断路器 | 触发条件 | 触发动作 | 恢复条件 |
|-|-|-|-|
| 社交媒体断路器 | 连续3天每天刷 > 2小时 | 通知提醒、可选限屏 | 连续3天每天 < 1小时 |
| 决策瘫痪断路器 | 超过预设决策时间 | 强制执行默认/随机选择 | 做出决策后自动恢复 |
| 过度分析断路器 | 连续3天分析 > 3小时/天 | 强制执行至少1件事 | 完成至少1个真实行动 |
| 情绪螺旋断路器 | 连续2天情绪 > 7/10 | 认知解耦+寻求支持 | 情绪 < 5/10 持续1天 |
| 自我批评断路器 | 10分钟内自我批评 > 3次 | 提醒+要求说1件好事 | 说出积极内容后恢复 |

### 5.3.2 断路器管理原则

```Plaintext
1. 断路器必须预设，不能等到触发时才制定
2. 断路器触发时，先执行预设动作，不做额外思考
3. 断路器是保护机制，不是惩罚机制
4. 定期审查断路器的有效性，必要时调整阈值
```

## 5.4 恢复协议

```Plaintext
flowchart TD
    A[Step 1: 识别崩溃] --> B{有即时危险?}
    B -->|是| C[立即寻求帮助]
    B -->|否| D[Step 2: 安全确认]
    
    D --> E{需要外部帮助?}
    E -->|是| F[联系支持网络]
    E -->|否| G[Step 3: 最小化恢复]
    
    G --> H[执行最小恢复清单]
    H --> I{清单完成?}
    I -->|否| F
    I -->|是| J[进入安全模式]
    
    J --> K[1-3天后]
    K --> L[尝试简化日环]
    L --> M{成功?}
    M -->|否| J
    M -->|是| N[升级到降级模式]
    
    N --> O[3-7天后]
    O --> P[尝试简化周环]
    P --> Q{成功?}
    Q -->|否| N
    Q -->|是| R[逐步恢复正常]
    
    R --> S[Step 5: 复盘与升级]
    S --> T[崩溃报告 + 系统升级清单]
```

## 5.5 反脆弱设计

### 5.5.1 反脆弱实践

| 实践 | 原理 | 操作 | 示例 |
|-|-|-|-|
| 刻意失败 | 小失败 = 疫苗 | 每月尝试1件可能失败的事 | 练习被拒绝、被批评 |
| 压力测试 | 测试极端情况 | 季度评估极端场景应对 | 低能量维持测试 |
| 多样性冗余 | 不把鸡蛋放一个篮子 | 检查单点故障风险 | 多收入/多关系/多技能 |
| 冲击日记 | 从冲击中学习 | 重大冲击后记录分析 | 定期回顾识别模式 |

## 6.2 A/B测试框架

### 6.2.1 A/B测试流程

```Plaintext
flowchart LR
    A[Step 1: 假设生成] --> B[Step 2: 测试设计]
    B --> C[Step 3: 执行测试]
    C --> D[Step 4: 结果评估]
    D --> E{决策}
    E -->|B优于A| F[采用B]
    E -->|A与B无差异| G[保留A]
    E -->|B劣于A| H[回滚到A]
    F --> I[Step 5: 固化]
    G --> I
    H --> I
```

### 6.2.2 A/B测试示例

```Plaintext
示例: 晨间协议时长测试

假设: "我相信如果晨间协议从5分钟延长到10分钟，动机质量会提升"

设计:
  A版本: 晨间5分钟（快速启动）
  B版本: 晨间10分钟（深度准备）
  
测试周期: 4周（A两周 + B两周）

评估指标:
  主指标: 本周动机质量分布
  副指标: 任务完成率、情绪评分

执行记录:
  周1-2 (A版本):
    - 平均晨间时长: 5.2分钟
    - 动机质量: 平均4.2/6
    - 任务完成率: 75%
    - 主观感受: "有点赶"

  周3-4 (B版本):
    - 平均晨间时长: 9.8分钟
    - 动机质量: 平均4.5/6
    - 任务完成率: 78%
    - 主观感受: "准备更充分"

评估:
  - 动机质量提升: 4.2→4.5 (+7%)
  - 任务完成率略升
  - 主观感受改善
  
决策: 采用B版本，更新为v1.3
```

## 6.3 废弃协议

### 6.3.1 废弃判断标准

```Plaintext
以下情况，考虑废弃某个协议:

1. 长期低执行率
   - 连续3个月执行率 < 30%
   - 原因不是外部因素，而是协议设计问题

2. 负面效果
   - 执行该协议后，相关指标变差
   - 主观感受持续负面

3. 功能重复
   - 该协议与其他协议功能高度重叠
   - 维护成本大于价值

4. 时代不适应
   - 外部环境变化导致协议不再适用
   - 核心假设已失效

5. 个人成长
   - 该协议已内化为自动行为，不再需要显式执行
   - 升级到更高级版本
```

## 6.4 从v1.0到v2.0的升级路径

### 6.4.1 升级触发信号

```Plaintext
准备升级到v2.0的信号:

1. 架构瓶颈
   - 当前架构无法支持新的需求
   - 协议之间冲突越来越多
   - 系统性能明显下降

2. 核心假设改变
   - 人生目标发生重大变化
   - 身份认同需要重构
   - 赛道类型根本改变

3. 数据积累足够
   - 有足够的历史数据支持深度分析
   - 模式识别变得清晰
   - 可以做出更精准的预测

4. 个人成长到位
   - 当前系统已不能推动成长
   - 需要更高级的系统
   - 准备好进入新阶段
```

### 6.4.2 升级执行阶段

| 阶段 | 时长 | 核心任务 |
|-|-|-|
| 深度盘点 | 1个月 | 回顾v1.0至今的数据，识别系统局限性 |
| 新架构设计 | 1个月 | 设计新的六层架构和协议体系 |
| 平行测试 | 2个月 | v1.x继续运行，v2.0测试 |
| 切换决策 | 1周 | 评估v2.0是否ready |
| 执行切换 | 1次 | 备份→切换→监控 |
| 过渡期支持 | 1个月 | 密集监控，快速迭代 |

## 7.3 常见问题FAQ

```Plaintext
Q: 如果我无法每天执行完整的日环怎么办？
A: 从简化版开始。晨间只做3件事：自由能对齐 + 身份提醒 + 能量评估。
   晚间只做2件事：今日亮点 + 明日准备。逐步增加，不要一开始就追求完美。

Q: 如果某个协议一直执行不下去怎么办？
A: 先分析原因：是协议设计问题还是执行能力问题？
   如果是设计问题，修改协议。如果是能力问题，考虑先降级要求。
   如果长期失败，考虑废弃该协议。

Q: 系统会不会太复杂而无法坚持？
A: 系统的目的是让你不需要意志力。复杂在前端设计，简洁在日常执行。
   如果日常执行感觉复杂，说明系统设计有问题，需要简化。
   记住：系统是为你的，不是你为系统。

Q: 我应该在什么时候进行A/B测试？
A: 在系统稳定运行2周后。选择一个你想改进的单一变量，
   用4周时间进行A/B测试。不要同时测试多个变量。

Q: 系统崩溃了怎么办？
A: 执行"崩溃恢复协议"。首先确认安全，然后执行最小恢复清单，
   然后逐步回到正常运行。不要急于恢复所有功能，慢慢来。

Q: 我需要使用什么工具来支持这个系统？
A: 最小工具集：一个笔记应用（记录日环、周环）、一个日历（时间块）、
   一个简单表格（追踪KPI）。不需要复杂软件，简单即可。
```

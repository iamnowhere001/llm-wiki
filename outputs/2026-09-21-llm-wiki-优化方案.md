# LLM Wiki 优化方案 —— 对照当下实践

> 一句话结论：**本库在「证据质量」这一维度上明显领先当下的公开实践，落后的是「规模与协作」这一维度。**
> 前者的差距是本库自己造出来的（项目层、`evidence_tier`、六类证据问题、L0/L1 核查分级）；
> 后者的差距是**公开实践踩过坑而本库还没踩到** —— 而其中两条，本库其实已经踩到了，只是没登记。

**体检基线（2026-09-21 11:38）**：452 页（`index` 口径）/ 458 页（`lint` 口径）｜ 7,378 条链接 ｜ 正文 338 万字符 ｜ raw 素材 145 份 ｜ `lint` 机器可查问题 **0 项** ｜ git 47 次提交。

## 一、对照基准：当下公开实践是什么样

参考三份材料（均为 2026 年 4 月后发布，即 Karpathy 原 gist 之后）：

| 来源 | 性质 | 关键信息 |
|---|---|---|
| Karpathy gist（2026-04-04，5,000+ stars / 5,000+ forks） | 模式原文 | 三层架构、三操作（ingest / query / lint）、「一次 ingest 触及 10-15 页」 |
| starmorph 指南（Dylan Boudro，2026-04-09） | 完整实践手册 | `outputs/` 目录、Obsidian 前端、QMD 检索、社区实现清单、Hacker News 批评 |
| kunalganglani 指南（作者每日运行 3 个月） | 踩坑实录 | **作用域化更新工作流**、六类失败模式、147 页 / 43 源的实测规模 |
| LLM Wiki v2（rohitg00） | 社区扩展 | 记忆生命周期、置信度评分、取代追踪、类型化关系、**多 agent 治理** |

**公开实践公认的规模天花板**：150–200 页开始退化（context 装不下整个 wiki，agent 开始「忘记」页面存在、建重复页、漏交叉链接）；实际退化阈值约 200K–300K token。

**本库当前 452 页 / 338 万字符 —— 已远超这个天花板，但没有出现对应症状。** 原因是本库有公开实践没有的东西：`index.md` 分层导航 + `lint` 的机器校验 + 站点构建判据。也就是说，**本库是用一套自制的补偿机制跑在公开实践的天花板之上**。这份方案要问的是：**这套补偿机制本身还有多少余量？**

## 二、本库领先的部分（不要动，反而是可输出的资产）

| 能力 | 公开实践 | 本库 | 备注 |
|---|---|---|---|
| **目标层** | 无 —— gist 完全没有「为什么收这份素材」 | 项目页 + 两类缺口表（文献缺口 / 未知缺口） | **本库独创**，对应 `AGENTS.md` §0 的「第 0 问」 |
| **证据层级** | 只有主观 `confidence` | `evidence_tier` 可计算（single / crossed / primary），`lint` 校验 | 外部无法区分「孤证」与「交叉验证」 |
| **来源独立性** | 多份素材即视为独立佐证 | **来源族识别** —— 会报出「名义交叉、实质同源」（当前 43 页） | 外部实践完全无此概念 |
| **证据问题分类** | lint 只做五类扫描（矛盾 / 孤儿 / 缺失概念 / 过时 / 调查空白） | **六类证据问题**（推广 / AI 生成 / 伪引注 / 弱引注 / 使用失真 / 过期引注），处理方式各不相同 | 外部的「矛盾」是单一类别 |
| **核查分级** | 无 | L0 事实核查（每次）+ L1 全文校准（命中触发条件） | 外部没有「核什么、核到什么程度」的判据 |
| **判矛盾的前置条件** | 无 | §3.9 命题分层 —— 判矛盾前先问两侧在不在同一层 | 外部把「符号相反」直接当矛盾 |
| **防臃肿** | 无（外部实测「wiki drift」是失败模式之一） | §6.1 八条硬约束 + `lint` 核法 | 本库已把 drift 变成可检查项 |
| **构建时机** | 无此问题（Obsidian 实时视图） | 五条判据 + `buildcheck` 内容指纹基准 | —— |
| **操作封装** | 才刚有 `wiki-skills` | 17 个 `llm-wiki-*` skill | —— |
| **前端** | Obsidian（graph view + backlinks + Dataview） | 自建单文件站点，**已有图谱视图与反向链接面板** | 该项已追平 |

**结论**：本库的「证据质量层」已经不是「优化」的问题，而是**可以反向输出的方法论**。`llm-wiki-research` 项目的 goal 是「写到能写出一篇对外文章的深度」—— 上面这张表就是那篇文章的核心素材，而公开实践里没有任何一份材料覆盖它。

## 三、优化项

按「不改会出事」到「改了更好」排序。

### P0-1 ｜ `index.md` 已膨胀到约 5 万 token，而它是每次会话的第一站

**症状**
`wiki/index.md` 84,075 字符（约 4–5 万 token）。而 `AGENTS.md` §4 与 `schema` §4.1 都要求**每次会话开始 / 每次查询都先读它**定位候选页。

**证据（可核）**
- `wc -c wiki/index.md` → 173,734 字节 / 84,075 字符
- 对比：公开实践建议 master index 控制在「几千 token」量级，agent 先读索引再定向加载页面
- 本库自己早已登记这个风险：`wiki/concepts/llm-wiki-pattern.md` 待办第一条 ——「页面数达到什么量级后，`index.md` 不再够用、必须上检索（见 [[qmd]]）？」
- **该待办至今未答，而阈值已经越过。**

**为什么这是 P0**
它是**每一次操作都要付的成本**，且随库增长线性变差。读一遍索引就占掉约 1/4 的上下文窗口，而查询还没开始。公开实践的「150-200 页退化」正是从这一步开始的 —— 本库用索引补偿了上下文问题，但索引本身正在变成新的上下文问题。

**修法（三选一，建议先做 A）**

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 索引分层** | `index.md` 瘦身为「主线导航 + 类型目录（只列 slug + 一行摘要）」，完整摘要移到 `index/<type>.md` 分片，按需加载 | 需要改 `wiki.py index` 的生成逻辑 + 站点 `DATA` 注入方式 |
| **B. 索引改检索优先** | 查询第一步改为 `wiki.py search`（BM25），`index.md` 降级为人类阅读用 | 需要先量测 BM25 在 452 页下的召回率；BM25 对中文二字组的切分是本库自实现的，质量未验证 |
| **C. 索引加「最近变更」顶栏** | 保留全量索引，但顶部先给「最近 N 次 ingest 触及的页面」—— 覆盖大多数查询的实际需求 | 最省事，但没解决根本问题 |

**验收判据**：`index.md` 的 token 量降到 **< 1 万**；且用 10 个真实历史查询做回归，定位候选页的命中率不低于分层前。

### P0-2 ｜ 并发会话写入无任何保护 —— 已经实际发生过至少 5 次

**症状**
本库允许（事实上是经常）多个会话同时写 `wiki/`，没有任何锁、没有 session 标识、没有分支约定。

**证据（可核，全在 `wiki/log.md`）**
- 行 294：`> [!warning] **本轮发现仓库存在并发写入**`
- 行 298：站点构建「⚠️ 该次构建是另一并发会话触发的，其时的页面数本库未记录」
- 行 635：模块八 12 份素材的 sources 页「由并发会话于 23:07-23:35 建好，本轮接手时 lint 为 0 项 —— 但它们的回填清单全部未执行」
- 行 637 / 1290：构建基准被并发会话改写，导致「上次构建时间」失去可比性
- 跨项目记忆里也有同型实测：**同一条消息里对同一文件发多个编辑，会静默丢失且工具仍返回成功**

**为什么这是 P0**
它已经造成了**三类实际损失**：① 审计线索断裂（上次构建时间不可比）；② 工作交接失败（建页与回填被拆到两个会话，回填静默挂账）；③ 基准文件被覆盖。而这三类的共同特征是 —— **没有任何机制会报错**。

**修法**

| # | 动作 | 说明 |
|---|---|---|
| 1 | `wiki.py` 加 `claim` / `release` 子命令 | 写 `.workbuddy-ai/lock.json`（含 session id + 时间戳 + 范围）。`ingest` / 批量改写前必须 claim，失败即中止 |
| 2 | log 条目加会话标识 | 每条 log 加 `[session:xxx]`，让「谁做的」可追 |
| 3 | `AGENTS.md` §3 加一条硬约束 | 「同一时刻只允许一个会话写 `wiki/`；并发会话只允许读」 |
| 4 | 或者更轻：git 分支约定 | 每个会话一个分支，`main` 只接受合并。代价是本库「编辑即自动 commit」的便利会受影响 |

**验收判据**：注入一个「两个会话同时 claim」的样本，确认第二个**必然失败并返回非零**（不要相信「没报错 = 没问题」）。

### P0-3 ｜ `raw/` 不可变这条铁律没有机器强制 —— 今天刚被突破一次

**症状**
`AGENTS.md` §3.1 把「`raw/` 不可变」列为**第一条硬约束**，§3.2 给了 8 条准入条件的例外。但**没有任何检查会发现 `raw/` 被改动** —— `lint` 只扫 `wiki/`。

**证据（可核）**
```
git show --stat 39695c2
  chore: 移除全部图片资源并同步清理引用与行号声明   (2026-09-21 11:02)
  - 删除 raw/assets 下 311 个图片（png/jpg/jpeg/gif）
  - raw/2026-09-18-*.md ... 各 2 +-（多份 raw 文件的 frontmatter 被改）
```
`raw/` 下文件出现在这次提交的改动清单里。

**要分清的两件事（这决定处置方式）**
- **frontmatter 改动**：`assets` 字段在 §3.2 的白名单里，**形式上合规** —— 但 §3.2 第 3 条要求「必须由人类裁定，LLM 不得自行修改」，且第 4 条要求「不得覆盖，只能追加」。
- **删除 311 个素材文件**：这**不在 §3.2 的例外范围内**。例外的标题是「清理历史遗留的**抓取元数据**」，作用域是 frontmatter 字段，不是素材文件本身。

**这里的真问题不是「这次改动对不对」，而是「规则拦不住」** —— 如果这次是北洛的决定（很可能是），规则仍然是失效的，因为**它是靠人事后检查发现的，不是靠机制阻止的**。

**修法**

| # | 动作 |
|---|---|
| 1 | `lint` 加一条「`raw/` 自上次构建以来有改动」检查（对比 git HEAD，或写一份 raw 清单指纹） |
| 2 | 明确裁定：**删除素材文件是否属于 §3.2 例外**。若属于，扩写 §3.2；若不属于，写明「需另开一条例外，且必须人类裁定」 |
| 3 | 复核 §3.2 第 4 条「不得覆盖，只能追加」与本次「移除全部图片引用」的关系 —— 引用被移除算不算「覆盖」？ |

**验收判据**：改动任意一个 `raw/` 文件后跑 `lint`，**必须报出非零**。若报不出来，这条检查就是装饰。

### P1-1 ｜ 回填没有「先列受影响页面」这一步（爆炸半径失控）

**症状**
`schema` §2 第 8 步是「回填：更新所有被影响的已有页面」。**没有前置的范围确认**，agent 直接改。

**证据**
- 公开实践把这条列为**「最多人问、而原 gist 几乎没涉及」**的核心缺口，原话是：**「永远不要不加限定地让 agent『更新 wiki』」**。其推荐流程是「先列受影响页面 → 人类圈定（agent 可能列 15 个，你只想改 5 个）→ 再外科手术式更新」
- 本库的实际症状：`pitfalls.md` 记载「sources 页的『建议回填』块不会自动更新状态 —— 下一轮会据此误判『全部未执行』（2026-09-21 实测：23 份页 121 条挂账里，绝大多数此前已落地）」
- log 行 635：「回填清单全部未执行」—— 建页与回填被拆开，回填静默挂账
- 本库的应对是**事后**核（六类特征回归校验），不是**事前**圈定

**修法**
在 §2 的第 7 步与第 8 步之间插入 **7.5 步**：

```
7.5 列出回填清单 —— 只列不改
    输出：目标页 slug + 打算改什么 + 依据哪一条要点
    人类圈定范围后再执行第 8 步
```

**好消息：本库已经有这个结构了** —— `sources` 页的「## 回填清单」正是「受影响页面清单」。问题在于它现在是**事后挂账**（改完才写），不是**事前审批**（写了才改）。**这是一次语义翻转，不是新建机制。**

**验收判据**：下一次 ingest 的 log 条目里，回填清单的**提出时间**早于**执行时间**；且清单条数与实际改动页数的差可解释。

### P1-2 ｜ 没有周期性检查 —— `lint` 靠人喊

**症状**
`schema` §5「体检」的触发条件是「人类说『检查一下知识库』时执行」。没有周期。

**证据**
- 公开实践明确要求：**每周**跑专门矛盾检查；**每新增 20-30 份源**做一次术语规范化；定期列出「30 天未更新但已有新素材」的页
- 本库有 `updated` 字段但**没有用它做任何查询**：实测 **241 页 `updated` 早于 2026-09-20**（占 53%）
- 本库有 167 页提到「矛盾」，但**没有一处机制会主动提醒「这两页现在冲突了」**

**修法**

| # | 动作 | 产出 |
|---|---|---|
| 1 | `wiki.py stale` —— 列出 `updated` 早于最近 N 次 ingest 的页 | 过时页清单 |
| 2 | `wiki.py drift` —— 列出同一 slug 的命名变体（外部实践报告「wiki drift」为高频失败模式） | 命名漂移清单 |
| 3 | 用自动化（定期任务）跑 `lint` + 矛盾扫描，报告落到 `outputs/` | 可追溯的体检快照 |

**为什么用自动化而不是「记得跑」**：本库已经有一条成熟判据 —— **「明确地不做」与「忘了做」在结果上一样，在过程上不同**。周期性检查同理。

**验收判据**：连续两周有报告产出；且报告文件的时间戳可证明它不是在人类提醒后才跑的。

### P1-3 ｜ 没有 `outputs/` 层 —— 产出物无处落地

**症状**
本库目录结构（`AGENTS.md` §2）只有 `raw/` / `wiki/` / `tools/` / `templates/`。**对外产出没有存放位置。**

**证据**
- 公开实践的标准结构里有 `outputs/`（dated reports, presentations, lint results）
- **本库项目页自己在喊这件事** —— `wiki/projects/llm-wiki-research.md` 的「产出」节：
  > 目前三个产出里有两个是**库内页面**，只有一个是真正的对外产出，而且还没开始。
  > 按 [[why-pkm-in-ai-era]] 自己的论证，**只产出库内页面等于没有产出** —— 这个项目目前正踩在这条线上。
- 至少两个项目的 `goal` 是「写到能写出一篇对外文章的深度」（`llm-wiki-research`、`peak-performance`），另有一个的 goal 是「在微信公众号发表一篇文章」（`traecode-pkm-article`）—— **三篇文章都没有家。**

**修法**
建 `outputs/`，放：对外文章草稿、演示稿、`lint` 报告快照、本方案这类诊断文档。
**不进 `wiki/`** —— 它不是知识网的一部分，不该被 `lint` 当知识页校验、也不该出现在站点图谱里。

**验收判据**：三篇对外文章各自有一个 `outputs/` 下的文件；`wiki/` 的页面数不因此增加。

### P2-1 ｜ 200 页残留「审核腔」—— 规则写了、源头没改（第二次）

**症状**
`schema` §6.1 第 4 条禁止「本库判断：X」「已登记」「不降级」这类审核腔。`lint` 能报，**当前报出 200 页**。

**证据**
- `lint` 输出：「残留审核腔自指语 (200)」
- 2026-09-21 已做过一轮全库冗余清理（log：「schema.md 70763 → 41385 字节」），但仍有 200 页
- 这是**同型问题的第二次实例**：跨项目记忆里记着「**规则写了、源头没改，等于没写**」—— 上次的实例是章节名统一改了产物没改模板

**这次源头在哪**
上次的源头是 `templates/`，改模板即可。**这次的源头是生成页面的会话本身** —— 写页面的那一刻没有这条约束，只能靠写完跑 `lint` 发现，而 `lint` 报的是「提示，不计入问题数」，于是没人处置。

**修法**

| # | 动作 |
|---|---|
| 1 | 把 §6.1 八条**做成 `llm-wiki-ingest` / `llm-wiki-derived-page-build` 等 skill 的写前自查清单**（写之前逐条过，而不是写完靠 lint） |
| 2 | 把禁止词做成机器词表（像 `tools/tags_vocab.py` 那样），供 lint 与 skill 共用一份 |
| 3 | 存量 200 页批量清理（按 `pitfalls.md` 的教训：**先分「纯声明」与「声明 + 实质信息」，后者只删声明子句**） |

**验收判据**：清完后**隔一周再跑一次**，计数不回升 —— 若回升，说明源头没改。

### P2-2 ｜ 42 页超长度上限 —— 判据能核出来，但没有处置流程

**症状**
`schema` §6.1 第 1 条定了上限（concept / entity ≤ 200 行，source ≤ 260，analysis ≤ 300）。`lint` 报 **42 页超标**，但标注是「提示，不计入问题数」。

**证据**
`lint` 输出：最长的是 `concepts/cybernetic-learning.md`（326 行，超 63%）、`analyses/modern-thinking-tools-review.md`（348 行）。

**这是「判据若核不出来就等于不存在」的变体**
那条说的是「缺核法」；这条是**核得出来，但没有触发任何处置**。结果是同一个：**规则在管，实际没管。**

**修法（二选一，不要停在中间）**
- **要么给处置**：超标的页进入拆页排期，`lint` 的提示升级为可跟踪的待办
- **要么承认是软约束**：把措辞从「上限」改为「建议值」，并说明超过多少必须拆

**验收判据**：`lint` 的超标清单要么在下降，要么规则里明确写了「不处理」的理由。

### P2-3 ｜ 101 页链接密度 < 1.5 —— 阈值本身待裁定

**症状**
`lint` 报 101 页正文链接密度低于 1.5 条/千字，即本库定义的「**清单式挂靠**」（只写进 `related` 字段，正文不引用）。

**证据**
- 最低于者 0.42 条/千字（11,767 字，5 条）—— 且**前 12 名全部是 `sources/` 页**（slug 形如 `2026-09-19-*`）
- `schema` §5 已自行标注：「**1.5 对素材摘要页偏高，已提待裁定**」

**修法**
**先裁定，再处置。** 本库知识页与素材摘要页的链接密度天然不同（摘要页的职责是「记录一份素材」，不是「参与论证」）。建议拆成两套阈值，分别实测标定。

**不要做的事**：为了数字好看回改阈值，也不要为了达标灌链接 —— `schema` §5 已经把这两条写死了。

### P2-4 ｜ 43 个 `crossed` 页实际是同源 —— 机制已知，待裁定

**症状**
`stats` 报出：96 个 `crossed` 页中 **43 个的全部支撑素材来自同一来源族** —— 名义交叉、实质同源。

**证据**
- `pitfalls.md` 已完整记载此机制，并给出三条判据：机制照跑（不改自动算出的值）、页内加显式警示、**别为了让它算对而删第二个来源**
- 根因清晰：`evidence_tier` 按「`sources` 字段的素材份数」算，**不区分来源族** —— 而机制**「看得到」来源族这件事**（`stats` 能报出来），只是没联动到 `evidence_tier`

**修法（本库已经诊断完毕，只差裁定）**
两条路，选一条：
- **A. 加字段**：`source_family` 或 `independent_sources`，让 `evidence_tier` 的判定基于独立来源数
- **B. 加取值**：`crossed` 拆成 `crossed-independent` / `crossed-same-family`

**注意**：本库已有判据「**归并失败时默认『各自独立』，不并族** —— 把真交叉误判成同源，比漏报同源代价更大」（`schema` §1.2）。所以这条路要么做得准，要么维持现状 + 页内警示。

### P3-1 ｜ 检索只有 BM25，且质量未验证

**症状**
`wiki.py search` 是自实现的 BM25 + 中文二字组。公开实践推荐 QMD（BM25 + 向量 + LLM 重排，Tobi Lutke 构建，Karpathy 推荐）。

**但这不该现在就做**：BM25 够不够用，取决于 P0-1 的选择。**先量测，再决定。** 测法：取 10 个真实历史查询，看 BM25 的 Top-10 命中率是否低于人工定位。

### 与原方案的三处差异（都需北洛知悉）

1. **P0-2 第 2 条「log 条目加会话标识」未执行。** 理由：会话 id 是 pid，对读者无意义；git commit 已有 author 与时间；本库刚清理过日志噪声。审计线索由锁文件承担。

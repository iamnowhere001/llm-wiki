## 三、五个新诊断

### D1 【P0】铁律 #1 的核法是空转的 —— `rawcheck` 永久红灯

**症状**

`lint` 退出码 **51**，51 项全部落在「`raw/` 已被改动（铁律：raw/ 不可变）」一类：
**37 项「内容已改动」+ 14 项「新增」**。这是全库唯一一类机器可查问题。

**根因（两层，第二层才是关键）**

1. **基准不在版本控制里。** 基准是 `.workbuddy-ai/raw-manifest.json`（14,162 字节，
   mtime **2026-09-21 12:03**，此后从未更新），而 `.workbuddy-ai/` 在 `.gitignore` 里。
   **它是一次性的、不可复现的、不在任何分支上的本地状态。**
2. **「新增」与「篡改」被合并计数。** 正常收录每天往 `raw/` 加文件 ——
   这是 `ingest` 的定义动作，**却被报成「违反铁律」**。于是：
   - 基准必然落后（§3.2 要求「改基准须人类裁定」，而收录是日常动作）；
   - 红灯必然常亮；
   - 而 `--write` 又会把「历史未裁定改动」一并固化为「正确」—— 09-21 附一已警告过这一点。

**后果：门禁退化**

本库已经为这个红灯发明了一套说法。`log.md` 原文：

> 「`lint`：机器可查问题 **51 项**（上一轮基线 48 + 本轮 raw 新增 3 项：2 份素材 + 1 份 PDF）。
> **判据是「无新增」**，这 3 项已逐项解释，不动基准。」

**「判据是『无新增』」这句话，等于把机器判据换成了人工记忆。** 而基线只写在 log 的散文里，
不在文件里、不在工具里。于是 `AGENTS.md` §3 第 12 条「每次改动后 `index` → `lint`」
这条硬约束**已经不可能被满足** —— 它要求的那道门永远是红的。

**真正的风险**：明天若真有人改了 `raw/` 里的一份素材，计数只会从 51 → 52，
**而所有人都已经习惯「有红灯，但都是老的那批」**。这正是 09-21 方案诊断并发写入时的那句话：
「没有任何机制会报错」。

**修法：核法改为 git 驱动，退役自建基准**

`raw/` 不可变的**权威记录就是 git** —— 自建一份指纹基准是对 git 的重复实现，且必然漂移。

| 类别 | `git status --porcelain raw/` 的形态 | 判定 |
|---|---|---|
| 新增未跟踪文件 | `?? raw/xxx.md` | **正常收录** —— 提示「记得 commit」，不计入问题数 |
| 已跟踪文件被改 | ` M raw/xxx.md` | **违规** —— 计入问题数，需裁定 |
| 已跟踪文件被删 | ` D raw/xxx.md` | **违规** —— 计入问题数，需裁定 |

**验收判据（双向，缺一不可）**

- 正向：`cp /tmp/x.md raw/2026-09-30-probe.md` 后跑 `lint` —— **必须不因这一项而红**；
- 反向：`printf '\n' >> raw/2026-09-18-bush-as-we-may-think.md` 后跑 `lint` —— **必须红且退出码非零**；
- 复现性：把仓库克隆到另一台机器，同一份 `raw/` 必须得到同一个判定（**自建基准做不到这一条**）。

**附带清理**：现存的 37 项「内容已改动」需要一次**收尾裁定** —— 它们对应的是
2026-09-19/20 批次 `author` 字段去「（讲稿）」后缀那次改动（09-21 附一已登记，至今无裁定记录）。
**不擅自回滚**：要么补一条裁定把它追认为合规，要么按 §3.2 走更正流程。

### D2 【P0】唯一给人看的文档，是过期最严重的文档

**症状**

`README.md` 是三层架构里唯一的「人类快速开始」，也是外部读者（含未来的你）的第一入口。

| 位置 | `README.md` 写的 | 实测 | 偏差 |
|---|---|---|---|
| 「当前内容」 | 已收录 **11 份素材**，编译为 **46 个页面** | **153 份 / 478 页** | **约 10 倍** |
| 「当前内容」 | 列出 12 个实体、5 个分析 | 73 个实体、21 个分析 | —— |
| 「工具链」 | 列 **9 个子命令** | **15 个** | 缺 `buildcheck` / `rawcheck` / `claim` / `release` / `chapter-audit` / `template-check` |
| 「素材重抓」 | 举例 `-r2` 后缀 | 正确 | —— |

**一个反向证据说明这确实发生了漂移**：README 里 `evidence_tier` 那段**是对的**
（已写 4 个取值、并解释了同源与独立的区别）—— 说明**有人改过它，但只改了被提醒的那一处**。
**没有机制保证 README 跟着库走。**

**为什么这是 P0 而不是 P2**

- 它是**唯一对外**的文档（其余规范文档都是对内、按需读的）；
- 它错的方式最危险 —— 「11 份素材 / 46 页」会让任何外部读者**低估这个库 10 倍**，
  而 `llm-wiki-research` 的 goal 正是「写到能写出一篇对外文章的深度」，外部读者是这个项目的验收方；
- 修法成本极低（见下）。

**修法：把「会过期的数字」从文档里赶出去**

| # | 动作 |
|---|---|
| 1 | 「当前内容」一节的**硬编码数字全部删除**，改为一句 `python3 tools/wiki.py stats` + 指向 `wiki/index.md` |
| 2 | 「工具链」清单**改为从 `wiki.py` 的用法表生成**（或至少加一条 `README-check`：README 中出现的 `wiki.py <cmd>` 必须真实存在，反向缺失不计） |
| 3 | 在 `AGENTS.md` §3 或 `schema` §2 收尾步骤里加一条：**新增子命令 / 页面数跨过量级时，README 是收尾清单的一项** |

**验收判据**：README 里不再出现任何会随收录变化的具体计数；
`README-check` 注入一个不存在的子命令，**必须报出**。

## 六、明确不建议做

| 不做 | 理由 |
|---|---|
| **为了 `lint` 归零而跑 `rawcheck --write`** | 会把 37 项「历史未裁定改动」固化成「正确」—— 09-21 附一已警告过同一件事。**归零不是目标，可信才是。** |

| **再新增一份「提案规范」文档** | 台账的落点是**已有的** `decisions` 总表 + `outputs/README.md`。新建一层文档，就是给 D3 制造第二个散落点 |
| **把本方案直接写进 `schema`** | 本库惯例：**裁定带出可复用判据时，默认登记为未决，不擅自落档**。本方案是提案 |
| **整理 725 个标签来搭主题导航** | 48% 只出现一次，top 标签是来源属性不是主题（09-29 体验方案已实测）。成本远大于收益，且立刻腐化 |
| **为 63% 的 `single` 页补来源** | 孤证是**诚实标注的结果，不是缺陷**。要改的是「哪几个 `single` 页最值得补第二来源」，不是把 63% 这个数字压下去 |
| **给 README 补一份英文版 / 加徽章** | 它现在的病是**内容过期**，不是**不够丰富**。先治过期，别加面积 |
| **顺手改 199 页存量自指语** | 存量已豁免，且判据本身核不出语义（09-21 裁定 C）。**新页约束已生效，存量不动是对的** |

# 知识库用户体验优化方案

> **一句话结论：这不是「功能不够」的问题，是「组织维度错配」的问题。**
> 站点已有的功能（BM25 + 候选收敛、反链、力导向图谱、TOC、账目折叠、j/k 翻页、`/` 聚焦）
> 比多数同类实现都全。**真正缺的三样东西，没有一样需要新写一套机制：**
> ① 界面按「文件类型」组织，而库按「项目 → 知识」组织 —— 两层结构不一致；
> ② 本库最独特的信号 `evidence_tier` **100% 存在于 frontmatter、0% 暴露在界面**；
> ③ 「新鲜度」字段 `updated` **已被批量操作污染，区分度为零**。
>
> 所以本方案的主线不是「加功能」，是**「把已经存在的结构接到界面上」**。

**体检基线（2026-09-29 10:5x，全部可复现）**

| 指标 | 值 | 核法 |
|---|---|---|
| 页面总数 | 473（concept 213 / source 152 / entity 73 / analysis 21 / project 8 / meta 6） | `wiki.py stats` |
| 正文总量 | 3,241,043 字符（站点全量注入） | 解析 `site/index.html` 的 `DATA` |
| 站点单文件 | 7,306,190 字节 | `Buffer.byteLength` |
| 链接 | 7,630 条，平均 16.1 条出链/页 | `stats` |
| 孤岛页（入链 0） | **0** | `DATA.backlinks` |
| 断链 | 15 个目标 / 36 次引用（多为模板占位符 `<slug>`、`...`） | 正文正则扫描 |
| 客户端解析开销 | 读文件 42ms + `JSON.parse` 10ms + 全库小写化 6ms | Node 22 实测 |

## 一、先定用户：谁在用，用來干什么

本库是**人机共读**的 —— 但这两类用户的「体验」是完全不同的东西，混在一起谈会两头落空。
本方案**以人类读者为主用户**，LLM 侧只保留必要的两条（见 §五 P2）。

### 主用户：北洛（唯一的人类读者）

从仓库的实际使用痕迹看，人类读者的界面有两个：`site/index.html`（单文件站点，可分享）
和 Obsidian（`.obsidian/app.json` 存在，配置为 `newLinkFormat: shortest`、附件指向 `raw/assets`）。
**本方案的优化目标是站点** —— Obsidian 的体验由 Obsidian 决定，本库改不了，也不该改。

五个场景，按实际频率排序：

| # | 场景 | 一句话描述 | 当前体验的瓶颈 |
|---|---|---|---|
| **S1** | **找回** | 「我记得库里写过 X，在哪一页？」 | 检索能用，但**不知道该猜它是 concept 还是 analysis** |
| **S2** | **主题通读** | 「把情绪这个主题系统地读一遍」 | 只能靠搜索堆结果，**没有策展过的阅读顺序** |
| **S3** | **判断可信度** | 「这个说法有多少证据撑着？」 | **这是本库的独有场景，而界面上完全无法完成** |
| **S4** | **对外产出** | 写文章时查库、引用、摘出一段 | 没有稳定章节级链接，引用只能指到整页 |
| **S5** | **巡检** | 「这周库里多了什么 / 什么过期了」 | `updated` 字段失效，**看不出任何东西的新旧** |

> **S3 是本库存在的理由，却是最不可能在界面上完成的场景。** 这是本方案判为 P0 的核心依据 ——
> 一个以「证据质量」为核心差异化资产的知识库，如果读者在它自己的界面上判断不了证据质量，
> 那这个资产就只存在于 `AGENTS.md` 和 CLI 里，不在产品里。

### 次用户：LLM / agent（编译者 + 检索者）

场景是「会话开始定位候选页」与「收录后回填」。这一侧 2026-09-21 已经做过一轮
（`index.md` 分层 43,891 → 8,416 token、`search --top` 暴露），**本轮只补两条遗留**（§五 P2-3、P2-4）。

## 二、诊断一：信息架构 —— 界面的分组维度与库的知识结构不一致

### 症状

侧栏 `ORDER = ["project","meta","source","entity","concept","analysis"]`，**按文件类型分组，组内平铺**。
而 `AGENTS.md` §0 与 `overview.md` 都写着：**「入口是项目，不是素材」**。

实测这两层的落差：

| 事实 | 数 | 含义 |
|---|---|---|
| 项目页能覆盖的知识页（concept+entity+analysis） | **303 / 307 = 99%** | 「按项目导航」在内容上**完全可行** |
| 未被任何项目引用的知识页 | 4 个 | 缺口极小，可单独兜底 |
| 知识页同时归属的项目数 | 1 个：251 页 ／ 2 个：35 页 ／ ≥3 个：17 页 | **重叠可控**，76% 归属唯一 |
| 侧栏里「概念」一组的条目数 | **213**（全部默认折叠，因 > `COLLAPSE_MIN=8`） | 折叠后等于**没有这一组** |
| 侧栏里「素材摘要」一组的条目数 | **152**，占全部条目 32% | 三分之一的主导航是**过程产物** |

**所以现状是**：库花了一整层（`projects/`）来回答「这些知识为了什么而存在」，
而界面把这层降级成侧栏第一条里的 8 个普通条目 —— 和 152 个素材摘要页并列。

### 这不是「要不要加导航」的问题

项目层**已经在内容里存在了**，只是没接到界面上。要做的不是新建一个主题分类体系
（那需要人工策展、会腐化），而是**让界面读已有的 `projects/` 出链关系**。

### 一个必须先排除的错误修法

**不要试图用标签来搭主题导航。** 实测：

- 标签总数 **725** 个
- **只出现 1 次：345 个（48%）**；≤2 次：553 个（76%）
- 出现 ≥10 页、勉强能当导航面的：**34 个**
- Top 标签是「万维钢」（227）、「得到课程」（202）、「现代思维工具」（105）—— **这些是来源属性，不是主题概念**

标签在本库的实际形态是**自由文本**，不是受控词表。指望靠整理它来做导航面，
等于要求 725 个标签里有 700 个被重新裁定 —— 成本远大于收益，且会立刻腐化回去。
**主题导航只能建立在已有的项目层上。**

## 三、诊断二：内容组织 —— 最有价值的信号，界面上一个都没有

### 症状

站点 `DATA.pages[i]` 注入的字段是：

```
slug, title, type, relpath, tags, status, updated, sources, links, body
```

而 `wiki/concepts|entities|analyses/` 的 frontmatter 里 **`evidence_tier` 覆盖率是 307/307 = 100%**：

| `evidence_tier` | 页数 | 占比 |
|---|---|---|
| `single` | 196 | 64% |
| `crossed-independent` | 56 | 18% |
| `crossed-same-family` | 43 | 14% |
| `primary` | 12 | 4% |

**10 个字段注入了，唯独漏掉这一个。** 后果是：

1. 读者打开任何一页看到的元信息是「类型 / 状态 / 更新日期 / 来源数 / 标签」——
   **唯独没有「这一页的结论有多少证据」**。而 64% 的页是孤证。
2. S3（判断可信度）场景在界面上**根本无法完成** —— 只能回 CLI 跑 `stats`，或去读 markdown 的 frontmatter。
3. 本库对外讲述的核心能力（`[2026-09-21-llm-wiki-optimization-plan]` 里列为「本库领先的部分」第一条）
   **在自己的站点上是隐形的**。

### 为什么这是 P0 而不是 P1

改动量极小：**build 时多带一个字段 + chips 里多一个色块 + 搜索结果里多一个标记**。
不需要新机制、不需要改内容、不需要裁定任何判据（`evidence_tier` 的值已由 `seed_evidence_tier.py` 算好并校验）。

**成本最低、价值最高 —— 这是本方案里性价比最高的一项。**

### 一个真张力（需要北洛裁定，不擅自决定）

`conventions.md` 的「清爽优先」明确要求**不要为了显得严谨而堆标记**。
`evidence_tier` 出现在界面上，有被读成「又一个审计腔标记」的风险。

两种呈现，代价不同：

| 方案 | 做法 | 风险 |
|---|---|---|
| **A. 常驻 chip** | 每页顶部一个「证据：交叉验证 / 孤证」色块 | 直接、可见；可能与「清爽优先」张力 |
| **B. 只在有信息量时显示** | `single` 不显示（默认态），`crossed-*` / `primary` 显示，`crossed-same-family` 显示为「交叉（同源）」 | 更克制；但读者学不到「默认就是孤证」这件事 |
| **C. 页脚一行** | 不在顶部 chip 区，放在页脚，「本页证据层级：single（仅 1 份素材支撑）」 | 最克制；首屏不可见，S3 场景仍要滚到底 |

**本方案倾向 B + C 组合**：顶部只在「有额外信息量」时出现（避免 64% 的页都挂一个无意义的「孤证」标），
页脚常驻一行完整说明（S3 场景有确定落点）。但这是**体验取舍，不是技术判断**，需裁定。

## 四、诊断三：新鲜度信号是假的

### 症状

`updated` 字段的分布：

| `updated` | 页数 |
|---|---|
| 2026-09-20 | **194** |
| 2026-09-19 | 135 |
| 2026-09-18 | 102 |
| 2026-09-21 | 20 |
| 2026-09-27 ~ 29 | 22 |

而 git 记录显示：**真正 2026-09-29 改动的页面只有 6 个**（`index.md`、`taste-terminology`、
`knowledge-is-the-bottleneck` 等）。194 页停在 09-20，是因为那一天做了一次**全库批量操作**
（commit `39695c2`「移除全部图片资源并同步清理引用」），`updated` 被成批刷新。

**结论：`updated` 现在记录的是「最后一次批量操作」，不是「这一页最后一次被真正修改」。**
它的区分度接近零（431/473 页集中在三天里）。

### 后果

任何基于 `updated` 的「最近更新」「过期检查」功能都是装饰。
2026-09-21 方案里的 P1-2 曾提议 `wiki.py stale`（列出 `updated` 早于最近 N 次 ingest 的页）——
**如果按现在的字段实现，它会一次性报出 400+ 页，等于没报。**

### 修法

新鲜度的真源头是 **git 提交时间**，不是 frontmatter。build 时从 `git log` 取每页的最后提交日期，
作为独立的 `commit_date` 注入；`updated` 保留但不再单独承担「新鲜度」语义。

**这也顺带解掉一个已有挂账**：`schema` §5 里「1.5 对素材摘要页偏高，已提待裁定」的链接密度阈值，
和这里的「字段被批量操作污染」是同型问题 —— **字段写了，但语义没被维护**。

## 五、其余五个维度

### 检索效率 —— 质量不差，缺三样小的

客户端 BM25 已经做了三处修正（候选收敛 / 最长命中加成 / 系统页降权、阈值 25% 截尾），
**实测设计是扎实的，这一项不该推倒重来**。缺的是：

| 缺口 | 现象 | 修法 |
|---|---|---|
| **无 facet** | 搜「情绪」出 60 条，混着 concept / source / analysis，不能收窄 | 结果区顶部加一行类型 / 证据层级过滤片 |
| **无同义词** | 「心流」与 `flow`、「情绪」与「感受」互不相通 | 一份手写同义词表（几十条即可，不需要词向量） |
| **零结果无引导** | 已有「整串无完整匹配」提示 —— 但没说接下来该干什么 | 零结果时给出最近的近似词 + 「按项目浏览」入口 |

CLI 侧（`wiki.py search`）有一个**默认值缺陷**：`--top` 默认 10，宽主题实测召回仅 13%，
需 `--top 30` 才到 70%、`--top 60` 到 97%（2026-09-21 已实测）。
**默认 10 对宽查询是错的** —— 这是 LLM 侧的体验问题，改默认值即可。

### 导航路径 —— 有深链，无路径

- 深链可用（`location.hash = slug`），但**不编码章节**，无法分享「某一节」。
- `overview.md` 里那条 12 步的「核心线索」（问题 → 主张 → 结构 → … → 输出回路）
  是**策展过的阅读顺序**，但界面上每一步都要回到 overview 看下一步 —— **路径存在，走不了**。
- 无「上一页 / 下一页」沿线索前进（现有 `j/k` 是在**可见列表**里移动，不是在**阅读序列**里移动）。
- 图谱 473 节点全量渲染（O(n²) 松弛，已有 `MAX_F` 保护不发散），但**全量图必然是毛球**。

### 交互流程 —— 键盘到位，缺两处

已有：`/` 聚焦搜索、`j/k` 或 `↑↓` 翻页、`Esc` 关抽屉、侧栏折叠状态持久化（localStorage）、
账目模式「折叠 / 置底」持久化、移动端 drawer。**这些是对的，不要动。**

缺：① 无搜索历史（S1 场景高度重复，历史能省一半输入）；② 无章节级复制链接。

### 可读性 —— 两项上一轮遗留，未处置

| 项 | 数 | 状态 |
|---|---|---|
| 残留审核腔自指语（「本库判断：」「已登记」「不降级」） | **200 页** | 2026-09-21 方案列为 P2-1，**未处置** |
| 超长度上限（concept/entity ≤200 行、source ≤260、analysis ≤300） | **42 页** | 列为 P2-2，**未处置** |
| 超 10,000 字符的页 | 99（超 20,000 的 11 页） | 界面无长度预期管理 |
| 最长页 `log` | 197,952 字符 | 单次渲染明显重 |

**这两项是纯粹的人类阅读体验问题，且已经在库里挂了一轮。** 它们不新增任何机制，
只是需要北洛先裁定「是拆页还是改规则」（见 §七）。

### 体积 —— 本地无感，分享是硬伤

**要诚实区分两件事**（这点容易被误判）：

- **本地打开：不是问题。** 实测读文件 42ms、`JSON.parse` 10ms、预处理 6ms。7.3MB 在本地磁盘上无感。
- **分享 / 远程访问：是硬伤。** 「单文件可分享」是自建站点相对 Obsidian 的核心优势之一，
  7.3MB 意味着邮件附件发不出去、移动网络打开要等、每次更新都要整份重下（无法增量）。

若 DATA 只注入「每页前 800 字符摘要 + 元数据」，正文按需加载：**3.24M → 0.38M 字符，降 88%**。
代价是失去离线全量（需要多文件产物或 fetch）。**这是取舍，不是必做** —— 判为 P2。

## 六、优化优先级

排序依据：**「改的是界面还是内容」×「是否需裁定」×「性价比」**。
**改界面且不需裁定的排最前**（可以立刻做）；**需裁定的单列**（§七）。

| 优先级 | 项 | 改什么 | 场景 | 需裁定 |
|---|---|---|---|---|
| **P0-1** | 注入 `evidence_tier` | `wiki.py` build + chips + 搜索结果 | S3 | **是**（呈现方式 A/B/C） |
| **P0-2** | 主导航改为「按项目」 | `wiki.py` buildNav + `ORDER` | S1 S2 | 否 |
| **P0-3** | 新鲜度改 git 驱动 | `wiki.py` build 取 `git log` | S5 | 否 |
| **P1-1** | 素材页退出主导航 | buildNav | S1 S2 | 否 |
| **P1-2** | 阅读路径（12 步线索 → 序列） | `wiki.py` + `overview.md` 结构 | S2 | 否 |
| **P1-3** | 搜索 facet + 同义词 + 零结果引导 | 站点 JS | S1 | 否 |
| **P1-4** | 长页长度预期 + 超长页单独处理 | 站点 JS | S2 | 否 |
| **P2-1** | 按需加载正文（体积 −88%） | 构建拆分为多文件 | 分享 | **是**（是否接受多文件） |
| **P2-2** | 图谱默认焦点图 | 站点 JS | S2 | 否 |
| **P2-3** | CLI `search` 默认 `--top 30` | `wiki.py` | LLM 检索 | 否 |
| **P2-4** | 审核腔 200 页 + 超标 42 页 | 内容（批量改写） | 可读性 | **是** |

## 七、实施步骤

### P0-1 ｜ 让证据层级在界面上可见

**症状**：307/307 页有 `evidence_tier`，站点注入 0 个。S3 场景在界面上无法完成。

| 步骤 | 动作 |
|---|---|
| 1 | `wiki.py` build：`DATA.pages[i]` 增加 `evidence_tier`（值直接读 frontmatter，不重算） |
| 2 | 页顶 chips 增加证据标记。**呈现方式待裁定（A 常驻 / B 仅额外信息量 / C 页脚一行）** |
| 3 | 搜索结果每条增加证据层级小标，使其可作为 facet |
| 4 | 反链面板、图谱节点着色可作为第二落点（可选） |
| 5 | `index` → `lint` → 判构建（改的是 `wiki.py` 内联模板，判据 4「模板变更」**可能命中**） |

**验收判据**：
- 打开任意一个 `crossed-same-family` 页（如 `ai-convergence`），界面上**必须**能看到「交叉（同源）」；
- 打开任意一个 `single` 页，按裁定方式能看到孤证标记；
- 注入一个「`evidence_tier` 缺失」的样本页，build 后**该页不得显示为已验证**（不要相信「没报错 = 没问题」）。

**预期效果**：S3 从「必须回 CLI 或读 frontmatter」变为「一屏内完成」；
本库对外讲述的核心能力第一次在自家产品里可见。

---

### P0-2 ｜ 主导航从「按文件类型」改为「按项目」

**症状**：侧栏按 type 分组，213 个 concept 默认折叠（等于没有）；而项目层已覆盖 99% 的知识页。

| 步骤 | 动作 |
|---|---|
| 1 | build 时注入 `project_of`：由 8 个项目页的 `links` 反查（**不新增 frontmatter 字段** —— 关系已经存在，只是没被读） |
| 2 | `ORDER` 改为：项目（默认展开）→ 类型（次级视图）→ 系统 |
| 3 | 归属多个项目的页（35+17 页）在**每个**所属项目下都出现，并在条目上标「也在：X」 |
| 4 | 4 个无归属页（`choice-overload`、`shane-parrish`、`mcraven-ten-lessons-vs-library`、`synthetic-vs-native-training-data`）归入「未归类」兜底组 —— **且这一组的存在本身就是待办信号** |
| 5 | 类型视图保留为 tab，不删除（S1 场景有时确实想按类型扫） |

**验收判据**：
- 侧栏首屏能看到 8 个项目组 + 各自页数；
- 任一知识页在侧栏**至少有一条可达路径**（用 20 个随机 slug 回归，全部可定位）；
- 「未归类」组的页数**随时间下降**，不上升。

**预期效果**：S1 从「猜它是 concept 还是 analysis → 在 213 条里找」变为
「从项目进 → 平均 30–50 条里找」；S2 第一次有了策展过的入口。
**这是把 `AGENTS.md` 声称的架构真正落到界面上。**

### P0-3 ｜ 新鲜度改由 git 驱动

**症状**：194 页 `updated` 同为 2026-09-20（批量操作污染），真实 09-29 改动仅 6 页。

| 步骤 | 动作 |
|---|---|
| 1 | build 时用 `git log -1 --format=%ad -- <relpath>` 取每页最后提交日期，注入 `commit_date` |
| 2 | 页顶 chips 的「更新 X」改为显示 `commit_date`（`updated` 保留在页脚备查） |
| 3 | 侧栏顶部增加「最近改动」入口：按 `commit_date` 倒序取前 20 页 |
| 4 | 2026-09-21 方案遗留的 `wiki.py stale` 若实施，**必须基于 `commit_date` 而非 `updated`**，否则会一次性报出 400+ 页 |

**验收判据**：注入一个「刚改过但 `updated` 仍是旧日期」的样本，界面**必须**显示为新；
反过来，`updated` 新但 git 未变的页不得显示为新。

**预期效果**：S5（巡检）从「看不出任何东西的新旧」变为「一眼看到本次会话动了哪几页」。

## 八、需要北洛裁定的四项（不擅自决定）

| # | 裁定点 | 选项 | 本方案的倾向 |
|---|---|---|---|
| **1** | `evidence_tier` 的呈现方式 | A 常驻 chip ／ B 仅额外信息量时显示 ／ C 页脚一行 | **B+C**：顶部克制、页脚完整，兼顾「清爽优先」与 S3 |
| **2** | 是否接受站点从「单文件」变「多文件」（换 −88% 体积） | 保持单文件 ／ 拆分为多文件 | **暂保持单文件** —— 本地无感，分享需求未证实为高频 |
| **3** | 200 页审核腔 + 42 页超标：拆页还是改规则 | 拆页 ／ 把「上限」改为「建议值」并写清超过多少必须拆 | **拆页** —— 改规则的代价是下一次还会超 |
| **4** | 4 个无归属页是否要补进某个项目 | 补 ／ 维持「未归类」 | **维持未归类** —— 它作为待办信号比强行归属更有用 |

## 九、明确不建议做的

| 不做 | 理由 |
|---|---|
| **推倒重写客户端检索** | 现有 BM25 的三处修正（收敛 / 最长命中加成 / 系统页降权）是 473 页规模逼出来的实战经验，重写会丢 |
| **整理 725 个标签来搭主题导航** | 48% 只出现一次；top 标签是来源属性不是主题。成本远大于收益，且立刻腐化 |
| **给知识页补 `confidence` 字段** | 知识页已有 `evidence_tier`（可计算、可校验）；再加主观 `confidence` 是两个尺度混用 |
| **把 `updated` 修准** | 修得了一次，下次批量操作还会污染。**换数据源（git），不修字段** |
| **为「150–200 页天花板」停止收录** | 2026-09-21 已判：天花板是公开实践的，本库用索引分层 + lint 补偿掉了 |
| **迁到 Obsidian 作为主界面** | 会丢掉 `buildcheck` 的内容指纹基准与单文件分享能力 |
| **把本方案直接写进 `schema`** | 本库惯例：**裁定带出可复用判据时，默认登记为未决，不擅自落档**。本方案是提案 |
| **顺手改 200 页审核腔** | 属 P2-4 且需裁定 3。未裁定前不动内容 |
